# Welding Tracker

Локальное веб-приложение для учета сварочных стыков трубопроводов.

## Стек

- TanStack Start + TypeScript
- Nitro Node server
- TanStack Query
- PostgreSQL 18 через Docker Compose
- Drizzle ORM
- Tailwind CSS + shadcn/ui-style components
- Vitest

## Запуск

```bash
curl -fsSL https://get.pnpm.io/install.sh | env PNPM_VERSION=12.0.0-rc.7 sh -
```

Откройте новый терминал, затем выполните:

```bash
pnpm install
pnpm db:up
pnpm db:migrate
pnpm dev
```

Команда применения миграций работает только из ветки `main` и останавливается до подключения к базе из любой другой ветки или при detached HEAD. Локальная команда дополнительно принимает в `DATABASE_URL` только `localhost`, `127.0.0.1` или `::1`, поэтому случайно подключиться ею к удаленной базе нельзя. После миграции команда также безопасно заполняет `ДНО` в полях дефектов ВИК, УЗК и ПВК для уже сохраненных годных результатов. Заполнение выполняется один раз; последующие миграции проверяют служебную отметку без повторного полного прохода по таблицам.

Откройте `http://localhost:3000`.

Если Docker CLI недоступен, установите Docker Desktop и повторите `pnpm db:up`.

## Локальная база

Локальная разработка должна работать только с локальной PostgreSQL из Docker:

```bash
DATABASE_URL=postgres://welding:welding@localhost:5432/welding_tracker
```

Для локальных секретов используйте `.env.local` или `.env`. Эти файлы не коммитятся.

## Развертывание в Coolify

Создайте приложение из Git-репозитория с build pack `Dockerfile`. `docker-compose.yml` нужен только для локальной PostgreSQL и не используется для production-развертывания приложения.

Настройки приложения:

- Dockerfile location: `/Dockerfile`;
- приложение не является статическим сайтом, publish directory оставьте пустым;
- exposed port: `3000`;
- один экземпляр приложения.

Dockerfile устанавливает pnpm 12 официальным standalone-скриптом, затем собирает TanStack Start и Nitro в отдельном build-этапе. Рабочий образ содержит Node.js, pnpm, `package.json` и готовую папку `.output`. Проверка жизни контейнера задана на `/health/live`: она отвечает 200 даже во время подготовки базы. `/health/ready` отвечает 200 только после миграций и переходов, иначе 503. Если Coolify переопределяет healthcheck, перед выпуском проверьте, что для запуска контейнера выбран `/health/live`, а не `/` или `/health/ready`; иначе новая версия может не заменить прежнюю. Реальные настройки хостинга локальные тесты не проверяют.

Добавьте переменные окружения:

```bash
NODE_ENV=production
HOST=0.0.0.0
PORT=3000
DATABASE_URL=postgres://user:password@postgres-host:5432/welding_tracker
DATABASE_POOL_MAX=5
DOCUMENT_TEMPLATE_STORAGE_PATH=/app/data/document-templates
MAINTENANCE_TOKEN=replace-with-a-long-random-secret
```

Создайте persistent volume с destination path `/app/data`. В нем хранятся только исходные Excel-шаблоны документов; записи журнала и метаданные остаются в PostgreSQL. Volume и базу нужно включить в резервное копирование.

Если production-база требует собственный корневой SSL-сертификат, добавьте `DATABASE_SSL_CA` со всем PEM-содержимым сертификата, включая строки `BEGIN CERTIFICATE` и `END CERTIFICATE`. Для Yandex Managed Service for PostgreSQL используйте `https://storage.yandexcloud.net/cloud-certs/CA.pem`. Приложение включает проверку сертификата и при наличии `DATABASE_SSL_CA` само удаляет конфликтующие SSL-параметры из `DATABASE_URL`.

Для ежедневного расчета фоновых кодов диспетчера создайте в Coolify Scheduled Task. Если планировщик работает в UTC, расписание `0 0 * * *` соответствует 03:00 МСК. Команда:

```bash
pnpm maintenance:dispatcher
```

Эндпоинт принимает только `POST` с секретом `MAINTENANCE_TOKEN`. Если фоновая проверка выключена в настройках приложения, задача безопасно завершится без расчета.

Перед переходом с Netlify или прежнего локального хранилища заранее скачайте каждый исходный Excel через `Настройки → Шаблоны документов → ⋯ → Скачать исходный шаблон`. После запуска Coolify замените соответствующие шаблоны этими файлами. Записи PostgreSQL не содержат сами Excel-файлы, поэтому одного переноса базы для шаблонов недостаточно.

### Production-миграции

Для миграции удаленной базы задайте отдельную переменную в локальном окружении администратора с установленными зависимостями проекта:

```bash
DATABASE_URL_REMOTE_FOR_MIGRATIONS=postgres://user:password@remote-host:5432/welding_tracker
```

Текущий согласованный порядок: **коммит → пуш → завершённый автодеплой → миграция и переходы → проверка → допуск пользователей**. Автодеплой отключать не требуется. До коммита/пуша согласуйте короткую паузу работы пользователей, дождитесь завершения сохранений и сделайте резервные копии PostgreSQL и volume `/app/data` (исходные Excel-шаблоны). Заранее проверьте способ восстановления обоих резервов.

После пуша дождитесь запуска нового образа именно опубликованного коммита и остановки всех прежних контейнеров/фоновых заданий. Новая версия в `NODE_ENV=production` показывает «Идёт обновление системы» и возвращает 503 на рабочие страницы, RPC и maintenance-запросы, пока база не готова. Старые открытые вкладки также не могут сохранить данные через новый сервер. Старый образ этой защиты не имеет: один лишь новый контейнер со статусом healthy не доказывает, что старые писатели остановлены.

Затем из чистой локальной копии опубликованного `main` запустите:

```bash
pnpm db:remote-migration --backup-confirmed --maintenance-window-confirmed --release-deployed-confirmed
```

Флаги — подтверждения администратора, не автоматическая проверка наличия резервов или остановки старого образа. Без любого флага команда останавливается до подключения. Она сохраняет прежние проверки удаляемых колонок и официальности, применяет сгенерированные миграции, заполняет пустые описания старых годных результатов и выполняет оба перехода данных, описанные ниже. Одновременный второй запуск отвергается. Успешный вывод содержит `phase: complete` и `ready: true`.

После успеха подождите до 5 секунд: рабочие разделы откроются без повторного деплоя. Проверьте `/health/ready` (200 и `ready: true`), программу линий, несколько знакомых цепочек, документы/скачивание шаблона, статистику и диспетчер. Производный индекс диспетчера отмечается устаревшим переходом и обновляется штатным механизмом новой версии; отдельного ручного изменения данных не требуется. Только после проверки возобновите работу пользователей.

При ошибке **не допускайте пользователей и не возвращайте старый образ на изменённую базу**. SQL-миграции могли уже завершиться, но два новых перехода и маркер готовности сохраняются одной транзакцией: неоднозначность или ошибка внутри неё не оставляет половину перехода и не открывает рабочие разделы. Сохраните текст ошибки; неоднозначные исключения разбираются отдельно, инструмент не удаляет их наугад. После устранения причины та же команда допускает повтор: уже применённые миграции не повторяются, завершённый переход не очищает документы заново. При потере соединения после фиксации результат команды может быть неизвестен: проверьте готовность и повторите ту же команду, не считайте обрыв доказательством отката. Полный откат выпуска — восстановление согласованных резервов БД/файлов и соответствующего старого образа, а не запуск локального `--restore` после работы пользователей.

Миграции `0029`-`0036` меняют набор колонок `weld_joints`, поэтому после их применения прежний образ приложения нельзя считать совместимым с базой. Если после миграции потребуется откат на прежний образ, одновременно восстановите сделанную перед релизом резервную копию PostgreSQL. Не запускайте старую и новую версии приложения параллельно во время этого обновления.

`db:remote-migration` не использует `DATABASE_URL` и завершится с ошибкой, если `DATABASE_URL_REMOTE_FOR_MIGRATIONS` не задана. До любого подключения команда требует ветку `main`, полностью чистую рабочую копию и точное совпадение локального `HEAD` с фактическим `origin/main`. Из рабочей или экспериментальной ветки, detached HEAD, с незакоммиченными файлами либо до публикации релизного коммита база не изменяется. Рабочий Docker-образ не содержит исходный код, зависимости проекта или Drizzle CLI, поэтому миграцию запускают из локальной копии репозитория, а не из терминала контейнера. Не добавляйте production-миграции в start command и не коммитьте настоящую строку подключения удаленной базы.

Сервер, порт, база и пользователь миграции должны быть заданы в основной части PostgreSQL URL. Переопределения цели через параметры вроде `?host=...` или `?port=...` запрещены до подключения, в том числе для локальных миграций; параметры TLS остаются допустимыми.

Историческая миграция `0037` добавляет таблицу страниц задач диспетчера. Прежний релиз требовал миграцию до открытия нового приложения. В текущем релизе запуск образа до миграции допустим благодаря описанной выше защите; рабочие запросы до подготовки базы не выполняются.

### Переход программы линий: 0038–0043

Эта серия добавляет реестр линий и резервные записи перехода, объектные ссылки исключений, сохранённые связи физических соединений и историю подтверждённого восстановления ошибочной катушки. Миграция 0042 специально сохраняет служебные связи удалённых записей: удаление строк катушки не должно автоматически возвращать вырезанное соединение. Новых миграций сверх 0043 для заключительной проверки не требуется.

**Одних SQL-миграций недостаточно для базы старой версии.** Полная команда `db:remote-migration` теперь включает:

- однократный переход `maintenance:line-program:v1`: согласованные свойства линий, первоначальный процент ПВК, ВИК = «да», резервное сохранение и удаление только старых автоматических послойных документов v1; обычные документы, шаблоны, результаты и нумерация сохраняются, конфликтующие требования дают СП-02;
- проверку привязки прежних принятых исключений к объектам внутри той же транзакции, применение только при отсутствии неоднозначностей; неразрешимые соответствия останавливают оба перехода;
- актуализация производного диспетчера по новой версии правил (62) и короткая проверка программы, цепочек, документов и статистики.

Переходы **не запускаются при старте или просмотре страниц**, а только явной командой выпуска. Локальный полный аналог — `pnpm db:release-local` с явно выбранной локальной `DATABASE_URL`; `pnpm db:prepare-release-local` выполняет только переходы после уже применённых миграций. Обычная локальная `pnpm db:migrate` остаётся схемной командой с прежним заполнением ДНО. Для запуска локальной production-сборки после неё нужна подготовка данных; dev-сервер этой блокировкой не ограничивается. Отдельные старые локальные инструменты перехода остаются локальными и не служат обходом защиты удалённого выпуска. Подготовка и тесты кода не разрешают агенту запускать production-команду.

Репетиция нового порядка: `node --import tsx scripts/verify-deploy-before-migration.ts` (или `--scale` для 200000 стыков). Она отказывается от существующей БД, создаёт только `127.0.0.1:5432/welding_tracker_test_deploy_first_20261004`, запускает готовую production-сборку на схеме 0037, проверяет блокировку запросов, миграции, откат обоих переходов при неоднозначности, повтор, защиту от одновременного запуска и открытие без рестарта. В конце удаляет только свою БД и останавливает свой сервер. Рабочая база и production не используются.

Локальная репетиция `node --import tsx scripts/verify-release-upgrade.ts --scale` сама создаёт **только отсутствующую** `127.0.0.1:5432/welding_tracker_line_program_test_release_20261003`, проверяет пустоту, ставит неизменённые сгенерированные миграции через `pnpm db:migrate`, вносит синтетическую историю на схеме 0037 и проверяет переход через 0041 к 0043. Сравнивает факты/документы, повтор миграций, переход и защищённое восстановление, физический расчёт и удаление катушки. В конце удаляет только свою БД. `--transition-regression` отдельно проверяет прежнюю утилиту перехода на 200/200000 строках. Рабочая база не используется.

Ресурсная репетиция использует отдельный локальный образ: `docker build --network=none --pull=false -f e2e/Dockerfile.resource -t welding-journal:release-resource-local-20261003 .output`. В образ копируется только готовая локальная сборка, без `.env` и исходных шаблонов. При отсутствующей E2E-БД запускайте сценарий отдельно: `E2E_USE_PRODUCTION_BUILD=1 AUDIT_CONTAINER_MEMORY_MIB=2048 AUDIT_CONTAINER_DEFAULT_HEAP=1 AUDIT_REBUILD_ROWS=200000 node --import tsx e2e/run.ts --config e2e/resource.config.ts e2e/tests/system-document-rebuild-scale.spec.ts`. Это 2 ГиБ RAM, стандартный heap Node 22 (~1048 МиБ), 2 CPU, без swap; PostgreSQL и браузер вне лимита. Без `AUDIT_CONTAINER_DEFAULT_HEAP=1` обвязка задаёт heap 1536/3072 для допустимых лимитов RAM 2048/4096 МиБ. `AUDIT_REBUILD_PACKETS=3` проверяет только три пакета для сравнения; для полного аудита эту переменную не задавайте. После аварийного прерывания отдельно проверьте удаление своей тестовой БД и контейнера. Это тестовые условия, **не настройки production**.

**Пакетная пересборка, 03.10.2026:** прежняя неограниченная операция, падавшая со стандартным heap, заменена подтверждаемыми пакетами до 200 целых документов. Дополнительные пределы — 60000 позиций, 8 МиБ состава и 64 МиБ заполненных фактов; превышающий предел документ явно оставляется неизменным, без обрезания. Атомарность действует на один пакет: ошибка следующего не отменяет уже сохранённые пакеты. Полный локальный проход на 200000 стыках / 100000 повторов сохранил все 800000 позиций, пересобрал 4000→8000 документов и оставил четыре чрезмерно больших исторических документа с видимым предупреждением. Пик контейнера — **510,2 МиБ, OOM 0**; 20 применений по 23–27 с, весь цикл применения с промежуточными предпросмотрами — 713 с. Первый предпросмотр — 24,86 с / 0,53 МБ. Это измерение одной последовательной работы, не минимальные требования и не гарантия параллельной нагрузки. Реальные ресурсы Coolify и HTTP-таймауты нужно подтвердить отдельно; автоматически менять production-настройки нельзя.

### Нормализация старых значений назначений

Одноразовый служебный скрипт приводит старые варианты `Да`, `ДА`, `1`, `Нет`, `НЕТ` и `0` в полях назначений ВИК, РК, УЗК, ПВК, ТВМТ и ПСТО к каноническим `да` и `нет`. Он не меняет схему, стыки, заявки, заключения, результаты, даты и служебные отметки времени.

По умолчанию команда работает только с локальной базой и выполняет транзакцию `READ ONLY`: она показывает точные значения и количества, но ничего не меняет. В этом же режиме PostgreSQL строит план будущего `UPDATE` через `EXPLAIN` без `ANALYZE`, поэтому запрос проверяется, но не исполняется.

```bash
pnpm maintenance:normalize-control-assignments
```

Если изменения допустимы, dry-run напечатает код подтверждения и готовую команду с `--apply`. Код связан с конкретной базой и текущим состоянием всех шести полей; после любого изменения данных старый код перестает подходить. Неизвестные значения полностью блокируют применение. Скрипт также останавливается при неожиданных триггерах, правилах перезаписи, RLS, вычисляемых целевых колонках или несовпадении схемы.

Удаленная проверка использует только `DATABASE_URL_REMOTE_FOR_MIGRATIONS`:

```bash
pnpm maintenance:normalize-control-assignments:remote
```

До подключения к удаленной базе команда требует чистую ветку `main` и точное совпадение `HEAD` с `origin/main`. Для удаленного применения дополнительно обязательны выданный dry-run код, `--backup-confirmed`, `--maintenance-window-confirmed` и `--release-deployed-confirmed`: последний флаг подтверждает, что версия приложения с постоянной нормализацией уже развернута. Применение выполняется одной сериализуемой транзакцией, меняет только шесть полей назначений и после обновления повторно проверяет данные; при любой ошибке вся транзакция откатывается. Команда никогда не запускается автоматически при старте, миграции или деплое.

## Проверка перед публикацией

Полная локальная проверка запускается одной командой:

```bash
pnpm verify
```

Она проверяет TypeScript, весь набор тестов, production-сборку и зависимости. Во время production-сборки дополнительно проверяется, что каждая серверная RPC-ссылка присутствует в манифесте TanStack Start; при несовпадении сборка завершается с ошибкой. Production-граф должен проходить аудит без исключений.

Пользовательские сценарии проверяются отдельно: `pnpm test:e2e`. Запускайте команду на `main`: она создаёт только отсутствующую одноразовую базу `welding_tracker_e2e` на `127.0.0.1:5432`, проверяет её имя и пустое начальное состояние, применяет существующие миграции через `pnpm db:migrate` и локальные переходы выпуска. Уже существующая база не заменяется: сначала разберите, не используется ли она другим запуском или для диагностики сбоя. После прогона удаляется только база, созданная текущим процессом; смена её PostgreSQL ID запрещает очистку. Рабочая и удалённая базы не используются. В набор включена проверка всех 33 настроек ДЗ через реальные серверные вычисления, сохранённые страницы/индекс PostgreSQL и виртуальное поле `dispatcherTasks`; два напоминания по срокам клейм проверяются отдельно и не попадают в индекс стыков.

Для проверки собранного релизного приложения сначала выполните `pnpm build`, затем `E2E_USE_PRODUCTION_BUILD=1 pnpm test:e2e`: тот же набор работает через `pnpm start` вместо dev-сервера, также только на одноразовой локальной базе.

В полном аудите временно разрешено одно предупреждение `GHSA-67mh-4wv8-2f99`: оно относится к старому внутреннему `esbuild` стабильного `drizzle-kit`, который используется только CLI миграций и не входит в production-сборку приложения. Исключение нужно удалить после появления совместимой стабильной версии Drizzle Kit.
