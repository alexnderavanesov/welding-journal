# Welding Tracker

Локальное веб-приложение для учета сварочных стыков трубопроводов.

## Стек

- TanStack Start + TypeScript
- Nitro Node server
- TanStack Query
- PostgreSQL 18 через Docker Compose
- Drizzle ORM
- Tailwind CSS + shadcn/ui-style components
- Vitest

## Запуск

```bash
curl -fsSL https://get.pnpm.io/install.sh | env PNPM_VERSION=12.0.0-rc.7 sh -
```

Откройте новый терминал, затем выполните:

```bash
pnpm install
pnpm db:up
pnpm db:migrate
pnpm dev
```

Команда применения миграций работает только из ветки `main` и останавливается до подключения к базе из любой другой ветки или при detached HEAD. Локальная команда дополнительно принимает в `DATABASE_URL` только `localhost`, `127.0.0.1` или `::1`, поэтому случайно подключиться ею к удаленной базе нельзя. После миграции команда также безопасно заполняет `ДНО` в полях дефектов ВИК, УЗК и ПВК для уже сохраненных годных результатов. Заполнение выполняется один раз; последующие миграции проверяют служебную отметку без повторного полного прохода по таблицам.

Откройте `http://localhost:3000`.

Если Docker CLI недоступен, установите Docker Desktop и повторите `pnpm db:up`.

## Локальная база

Локальная разработка должна работать только с локальной PostgreSQL из Docker:

```bash
DATABASE_URL=postgres://welding:welding@localhost:5432/welding_tracker
```

Для локальных секретов используйте `.env.local` или `.env`. Эти файлы не коммитятся.

## Развертывание в Coolify

Создайте приложение из Git-репозитория с build pack `Dockerfile`. `docker-compose.yml` нужен только для локальной PostgreSQL и не используется для production-развертывания приложения.

Настройки приложения:

- Dockerfile location: `/Dockerfile`;
- приложение не является статическим сайтом, publish directory оставьте пустым;
- exposed port: `3000`;
- один экземпляр приложения.

Dockerfile устанавливает pnpm 12 официальным standalone-скриптом, затем собирает TanStack Start и Nitro в отдельном build-этапе. Рабочий образ содержит Node.js, pnpm, `package.json` и готовую папку `.output`; HTTP health check на `/` уже задан в образе.

Добавьте переменные окружения:

```bash
NODE_ENV=production
HOST=0.0.0.0
PORT=3000
DATABASE_URL=postgres://user:password@postgres-host:5432/welding_tracker
DATABASE_POOL_MAX=5
DOCUMENT_TEMPLATE_STORAGE_PATH=/app/data/document-templates
MAINTENANCE_TOKEN=replace-with-a-long-random-secret
```

Создайте persistent volume с destination path `/app/data`. В нем хранятся только исходные Excel-шаблоны документов; записи журнала и метаданные остаются в PostgreSQL. Volume и базу нужно включить в резервное копирование.

Если production-база требует собственный корневой SSL-сертификат, добавьте `DATABASE_SSL_CA` со всем PEM-содержимым сертификата, включая строки `BEGIN CERTIFICATE` и `END CERTIFICATE`. Для Yandex Managed Service for PostgreSQL используйте `https://storage.yandexcloud.net/cloud-certs/CA.pem`. Приложение включает проверку сертификата и при наличии `DATABASE_SSL_CA` само удаляет конфликтующие SSL-параметры из `DATABASE_URL`.

Для ежедневного расчета фоновых кодов диспетчера создайте в Coolify Scheduled Task. Если планировщик работает в UTC, расписание `0 0 * * *` соответствует 03:00 МСК. Команда:

```bash
pnpm maintenance:dispatcher
```

Эндпоинт принимает только `POST` с секретом `MAINTENANCE_TOKEN`. Если фоновая проверка выключена в настройках приложения, задача безопасно завершится без расчета.

Перед переходом с Netlify или прежнего локального хранилища заранее скачайте каждый исходный Excel через `Настройки → Шаблоны документов → ⋯ → Скачать исходный шаблон`. После запуска Coolify замените соответствующие шаблоны этими файлами. Записи PostgreSQL не содержат сами Excel-файлы, поэтому одного переноса базы для шаблонов недостаточно.

### Production-миграции

Для миграции удаленной базы задайте отдельную переменную в локальном окружении администратора с установленными зависимостями проекта:

```bash
DATABASE_URL_REMOTE_FOR_MIGRATIONS=postgres://user:password@remote-host:5432/welding_tracker
```

После объединения, проверки и публикации релизного коммита в `main`, но перед открытием новой версии приложения запустите из этой ветки:

```bash
pnpm db:remote-migration
```

Перед применением миграций команда сверяет фактический набор служебных колонок с историей Drizzle и проверяет все 27 удаляемых колонок РФА, СТЛС и МКК. При расхождении схемы с историей или при наличии значения хотя бы в одной удаляемой колонке процесс останавливается до изменения данных и схемы. Когда одновременно существуют старый `status` и новый `officiality`, значение `status` копируется только в пустой `officiality`; разные непустые значения считаются конфликтом и также останавливают процесс без перезаписи. После миграций команда выполняет соответствующее заполнение старых годных результатов.

На время финального production-релиза остановите запись пользователей: временно отключите автоматический деплой по push, включите режим обслуживания и сделайте резервную копию PostgreSQL и persistent volume. Затем опубликуйте проверенный релизный коммит, выполните миграцию, вручную разверните именно этот коммит, проведите короткую проверку и только после этого возобновите работу. Это исключает запуск новой версии на старой схеме и появление новых значений между защитной проверкой и удалением старых колонок.

Миграции `0029`-`0036` меняют набор колонок `weld_joints`, поэтому после их применения прежний образ приложения нельзя считать совместимым с базой. Если после миграции потребуется откат на прежний образ, одновременно восстановите сделанную перед релизом резервную копию PostgreSQL. Не запускайте старую и новую версии приложения параллельно во время этого обновления.

`db:remote-migration` не использует `DATABASE_URL` и завершится с ошибкой, если `DATABASE_URL_REMOTE_FOR_MIGRATIONS` не задана. До любого подключения команда требует ветку `main`, полностью чистую рабочую копию и точное совпадение локального `HEAD` с фактическим `origin/main`. Из рабочей или экспериментальной ветки, detached HEAD, с незакоммиченными файлами либо до публикации релизного коммита база не изменяется. Рабочий Docker-образ не содержит исходный код, зависимости проекта или Drizzle CLI, поэтому миграцию запускают из локальной копии репозитория, а не из терминала контейнера. Не добавляйте production-миграции в start command и не коммитьте настоящую строку подключения удаленной базы.

### Нормализация старых значений назначений

Одноразовый служебный скрипт приводит старые варианты `Да`, `ДА`, `1`, `Нет`, `НЕТ` и `0` в полях назначений ВИК, РК, УЗК, ПВК, ТВМТ и ПСТО к каноническим `да` и `нет`. Он не меняет схему, стыки, заявки, заключения, результаты, даты и служебные отметки времени.

По умолчанию команда работает только с локальной базой и выполняет транзакцию `READ ONLY`: она показывает точные значения и количества, но ничего не меняет. В этом же режиме PostgreSQL строит план будущего `UPDATE` через `EXPLAIN` без `ANALYZE`, поэтому запрос проверяется, но не исполняется.

```bash
pnpm maintenance:normalize-control-assignments
```

Если изменения допустимы, dry-run напечатает код подтверждения и готовую команду с `--apply`. Код связан с конкретной базой и текущим состоянием всех шести полей; после любого изменения данных старый код перестает подходить. Неизвестные значения полностью блокируют применение. Скрипт также останавливается при неожиданных триггерах, правилах перезаписи, RLS, вычисляемых целевых колонках или несовпадении схемы.

Удаленная проверка использует только `DATABASE_URL_REMOTE_FOR_MIGRATIONS`:

```bash
pnpm maintenance:normalize-control-assignments:remote
```

До подключения к удаленной базе команда требует чистую ветку `main` и точное совпадение `HEAD` с `origin/main`. Для удаленного применения дополнительно обязательны выданный dry-run код, `--backup-confirmed`, `--maintenance-window-confirmed` и `--release-deployed-confirmed`: последний флаг подтверждает, что версия приложения с постоянной нормализацией уже развернута. Применение выполняется одной сериализуемой транзакцией, меняет только шесть полей назначений и после обновления повторно проверяет данные; при любой ошибке вся транзакция откатывается. Команда никогда не запускается автоматически при старте, миграции или деплое.

## Проверка перед публикацией

Полная локальная проверка запускается одной командой:

```bash
pnpm verify
```

Она проверяет TypeScript, весь набор тестов, production-сборку и зависимости. Во время production-сборки дополнительно проверяется, что каждая серверная RPC-ссылка присутствует в манифесте TanStack Start; при несовпадении сборка завершается с ошибкой. Production-граф должен проходить аудит без исключений.

В полном аудите временно разрешено одно предупреждение `GHSA-67mh-4wv8-2f99`: оно относится к старому внутреннему `esbuild` стабильного `drizzle-kit`, который используется только CLI миграций и не входит в production-сборку приложения. Исключение нужно удалить после появления совместимой стабильной версии Drizzle Kit.
