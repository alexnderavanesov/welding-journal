# «Выбрать найденные»: повторная проверка линии и стыка

**Устойчивое ухудшение не подтвердилось.** Сохранённая сборка до оптимизации и итоговая C6 повторно сравнены в Chrome на одинаковых 200000 синтетических стыков. При сопоставимых сценариях линия и стык быстрее; откат или изменение рабочего кода не потребовались. Прежние +3,6% / +4,7% из короткой серии нельзя использовать как итоговую оценку этих действий.

## Новое сравнение

Время от реального нажатия до готовых строк и итогов таблицы. Медианы десяти последовательных применений каждого фильтра, включая первое применение; миллисекунды округлены. Без замены ответов и изменения кэшей.

| Фильтр столбца | До | C6 | Сокращение времени |
| --- | ---: | ---: | ---: |
| Проект | 430 мс | 347 мс | 19% |
| Шифр | 414 мс | 339 мс | 18% |
| **Линия** | **480 мс** | **398 мс** | **17%** |
| **Стык** | **737 мс** | **579 мс** | **21%** |
| Дата сварки | 456 мс | 364 мс | 20% |
| Итоговый результат | 447 мс | 364 мс | 19% |

Дополнительно по два применения линии и стыка после **31 секунды ожидания внутри уже открытого фильтра**. Сама пауза не входит в замер:

| Действие после паузы | До | C6 |
| --- | ---: | ---: |
| Линия | 478 / 512 мс | 430 / 429 мс |
| Стык | 1814 / 1795 мс | 1644 / 1630 мс |

Серверная запись SQL подтвердила: в каждом из десяти быстрых выборов стыка обе версии использовали готовый список; в обоих проходах после паузы обе заново читали 200000 вариантов. Старый холодный путь остаётся: запрос списка после паузы занял 1169–1184 мс до и 1113–1156 мс после. Это два контрольных воспроизведения, не оценка частоты редких задержек.

## Почему прежняя таблица показывала ухудшение

- **Линия:** три старых прохода 713 / 480 / 480 → 647 / 498 / 414 мс. Загрузка строк ускорилась во всех трёх. Во втором проходе ответ итогов занял 167 вместо 96 мс; этот отдельный эпизод изменил медиану. Причина именно того медленного ответа итогов не установлена. Новые десять повторов ухудшение не воспроизвели.
- **Стык:** 982 / 696 / 714 → 747 / 1664 / 580 мс. Во втором проходе запрос вариантов занял 1170 вместо 112 мс; загрузка строк и итогов при этом ускорилась. В исходных трёх проходах попадание в кэш не записывалось, поэтому его состояние задним числом не объявляется доказанным. Повторная проверка воспроизвела такой же долгий путь при подтверждённом истечении кэша **в обеих версиях**. Кроме того, прежняя отдельная серия из 20 повторов уже показывала улучшение 714 → 580 мс.

Вывод: отдельные долгие ответы были реальными, но короткая серия смешивала разные состояния и не доказывала регрессию оптимизации. Уточнена интерпретация; исходные невыгодные замеры сохранены.

## Проверка и границы

- Два независимых локальных production-mode сервера, отдельные одноразовые БД `127.0.0.1:5432/welding_tracker_e2e`, одинаковые данные и последовательность. Порядок запусков: исходная версия → C6. Старая сборка проверена по сохранённому SHA256; только в её одноразовой БД штатный диагностический guard воспроизвёл отсутствие нового индекса.
- **128 применений фильтров**, сбросы и 258 проверок видимых результатов: совпали точные ID/порядок видимых строк и полные количества. Проверки не обходят каждую найденную строку. Фокус, ограниченное число отображаемых строк и ошибки браузера проверялись существующим сценарием.
- Для линии и стыка совпали имена и размеры ответов запросов в каждом измерении. Отдельные чтения контекста диспетчера сохранены в данных: в первом выборе шифра исходной версии один такой ответ завершился после готовности таблицы. Его не вычитали из времени; полное число начатых запросов не выводится из ResourceTiming. Старая проверка полного RPC-accounting остаётся отдельным свидетельством.
- Оба браузерных запуска прошли. TypeScript и `git diff --check` прошли; после замеров изменены только название диагностического теста и пояснение его охвата. Полный E2E повторно не запускался: рабочий код, схема, сроки кэша и проверки актуальности в этой задаче не менялись. Safari, ЛНК/ПСТО и документы здесь заново не измерялись.
- Добавлен только opt-in диагностический режим в существующую E2E-проверку и её локальный SQL-наблюдатель. Исходные артефакты не переписаны; оба runner завершили собственные серверы и удалили собственные тестовые БД. Основная локальная БД и production не изменялись; commit/push/deployment не выполнялись.

Подпись исправлена для следующих запусков, исходные измерения сохранены.
