#### Критерии, которые нельзя потерять при проверке

- В **допуске клейма** группы — набор разрешённых материалов, без сторон 1/2 и без ограничения «не более двух», которое относится к стыку. Порядок выбора групп в допуске не меняет его смысл. Общие D/T, сроки и выбранные способы этой записи относятся к каждой выбранной группе; разные области допуска описываются отдельными записями, а не назначением сторонам трубы.
- В **стыке** одна группа остаётся одной записью (например, М01); две группы имеют порядок: первая — D1/T1, вторая — D2/T2. Перестановка групп не меняет размеры и другие поля материалов. Журнал, фильтр, импорт/экспорт и печать сохраняют порядок; только статистика объединяет обратные пары.
- Для разнородных С- и У-стыков проверяются обе стороны. Для каждого официального сварщика нужны обе группы в его участвующем способе сварки. - Два загрузчика контекста программы/цепочки падали с `Maximum call stack size exceeded`, когда один SQL-пакет возвращал 200000 строк: ограничение 500 линий не ограничивает число стыков. Устранена оставшаяся старая фраза в подтверждении «Не отстранять»: ремонты не увеличивают счётчик первичного брака РК/УЗК.

Общая математика используется программой, предварительным изменением, сервером, согласованиями и диспетчером. Независимые численные проверки включают округление, совместные/сменённые клейма, отсутствие кандидатов и предел 200000 соединений.

Исторический брак S1 не мешает завершению после годного ремонта/катушки, но сохраняется в истории и применимом доборе. R/W не увеличивают физическую численность, процентный зачёт и добор.
- Удаление обеих сторон катушки не восстанавливает физически вырезанный источник молча. СП-04 остаётся до исправления истории и отдельного защищённого подтверждения ошибочной замены. Проверяются связи через удалённые узлы, оставшиеся/перенесённые продолжения, отсутствие документов, корректный финал, версия и токен предпросмотра. Закрытие/отмена ничего не меняют; повторное подтверждение не создаёт второй факт восстановления.

- Неофициальность/неактуальность приостанавливает активный СП-03, но не удаляет обязательства ремонта. После возврата обоих признаков требование возвращается. Назначения согласованы между карточкой, программой, послойным действием и объединённой записью импорта.

Создание официального S1R1 рядом с неофициальным тёзкой больше не блокируется наличием тёзки; обязательные методы наследуются от S1 без копирования чужих результатов.

Сохранение меняет только актуальность и служебные версии, сохраняя факты и документы. Установлена версия расчёта **61** для существующих записей. Найдено и исправлено ложное незавершение годной катушки после исключения всей старой цепочки: исторические предшественники больше не теряются при проверке её происхождения.

Старые противоречивые факты не удаляются, отдельная ДЗ для них не вводится по решению пользователя. Чтение, возврат официальности и штатное исправление проверены на локальных исторических фикстурах. Наличие таких записей на production не проверялось.

В браузере проверены оба направления, смена официальности после предпросмотра, отказ без потери документов и успешный повтор после восстановления. Новых запросов для защиты не добавлено.

## Нагрузка и оставшиеся риски

- Текущий браузерный замер окна назначений: 500/1000 стыков — **2 запроса деталей** на открытие и сохранение; открытие 2,06/2,58 с, поиск 42/48 мс, сохранение 603/672 мс. Ответ после сохранения 1,48/2,96 МБ: запросы не размножаются, но объём полной строки остаётся риском крупных линий.
- Переполнение стека в загрузчике пересборки документов воспроизведено на 200000 документов и исправлено: выборка больше не передаётся аргументами `push(...)`. Регрессия реального загрузчика с подменённой БД проверяет все ID и постоянное число загрузок: 4 индекса, 1 чтение строк, 1 настроек, 1 счётчиков. Реальный PostgreSQL-замер выше охватывает 200000 изменяемых позиций в 1000 документах, а не 200000 отдельных документов.
- Квадратичный поиск удаляемых позиций при переносе НК до ТО заменён набором ID. Регрессии 24/200000 позиций падали до исправления; после установлен линейный предел обращений к ID, чужие методы сохраняются. Это проверка сложности обработки, не времени всей транзакции с документами.
- Новый реальный замер на отдельной пустой локальной БД с 200000 стыков: кандидаты заявок ЛНК — **8 SQL / 1057 мс / 500 строк**, НК до ТО — **8 SQL / 693 мс / 500 строк**, сводка ПСТО — **2 SQL / 2181 мс**, кандидаты ПСТО — **7 SQL / 191 мс / 500 строк**. Пустые выборки результатов ЛНК/ПСТО/ТВМТ — **3 SQL**, 2615/410/392 мс; заявок ТВМТ — 3 SQL / 387 мс. Это не проверка гидратации больших непустых результатов. БД `127.0.0.1/welding_tracker_load_200k` после измерения удалена; рабочая БД не затронута.
- Новая синхронизация ролей после подтверждённой перестройки переиспользует уже загруженную линию. Для одной изменённой цепочки среди 24/1024/200000 записей регрессия проверяет **1 чтение состояния + 1 пакетную запись** без обновления посторонних цепочек. Без переименования дополнительных SQL нет. Это проверка количества запросов с подменой исполнителя, не новый нагрузочный замер PostgreSQL; реальные сохранения и отмены отдельно проверены в E2E.

Это реальный загрузчик PostgreSQL без серверного кэша, не только чистая функция. N+1 нет, но **11,5 с и ответ 4,5 МБ остаются существенным риском** общей сводки. Повтор защиты удаления — 4/5 SQL, 12/1957 мс.

Реестр без печатной части — **8 SQL**, 27/8166 мс, ответ 583/585787 байт. N+1 здесь не обнаружен, но **18,9 и 8,2 с остаются риском отзывчивости**, а не доказательством достаточной скорости.
- Предпросмотр восстановления: одинаковое ограниченное число запросов на линиях 24/1024; поиск ветки среди 200000 сохранённых связей — 17 SQL / 49 мс при 200 стыках самой линии. Гигантская линия в 200000 строк этим не покрывается. Полная строка программы со всеми данными остаётся риском размера ответа.
- Новая группировка актуальности проверена на 200000 сохранённых узлов без повторного обхода предков. PostgreSQL-предпросмотр / сохранение на линии 24/1024/200000 стыков: **11/13 SQL** при каждом размере, оба действия вместе **25/27/3250 мс**, включая защиту настроек. Ответ ограничен 100 записями; исчезнувшая при изменении состава последняя страница корректно возвращает оставшиеся записи. Focus/reconnect не повторяют запрос.
- Чистый расчёт завершённости 200000 строк / 100000 коротких веток: 800000 чтений исходных записей, **8490 мс**. Это не PostgreSQL/HTTP и не доказательство линейности всех внутренних алгоритмов. Для патологически длинной истории в прочих обходах предков остаётся риск повторной работы.
- Повторный замер версии 60 после оптимизации нормализации статусов: реестр 200/200000 стыков — **8/8 SQL**, 28/7737 мс под CPU-профилировщиком вместо 35/11123 мс; ответ 606/608787 байт. Повторы без профилировщика — около 7,6–7,7 с. Регрессия нормализации снижает число преобразований 15000 → 2000 при тех же входах/результатах. SQL исторических кандидатов: **1/1 запрос**, 7/362 мс, независимо подтверждены 200/200000 кандидатов.
- Новая защита удаления: **4/5 SQL** на 200/200000 выбранных строках; дополнительный запрос — второй пакет из 500 линий, не N+1. EXPLAIN выявил полный проход почти 200000 посторонних строк при проверке одной линии: обычное соединение по ID заменено точечным LATERAL-поиском после исключения выбранных ID. Регрессия проверяет отсутствие чтения таблицы стыков, когда нет оставшихся потомков, до/после ANALYZE. До исправления EXPLAIN — 3324/98 мс и почти полный проход, после — 83/6,5 мс без постороннего чтения. Весь guard после ANALYZE — **16/1904 мс**; это чтение-проверка, не время массового удаления и синхронизации документов. ANALYZE выполнялся только в одноразовой тестовой БД; новой миграции нет.
- Защиты результата/дубля/официальности/переноса используют загруженные заблокированные данные, дополнительных SQL/RPC не требуют. Загрузка дублей на 1/1000/200000 строк проверена как один запрос с массивом параметров и линейное сопоставление; это тест с подменённой БД, не новый замер PostgreSQL.
- Матрица диспетчера: 30 настроек, 28 сохранённых цепочек, 57 фикстур; refresh 34 SQL, виртуальное поле 1 SQL/страницу, обновление продолжения 32/32 SQL. Проверены возврат актуальности, coalescing, scoped-refresh, focus/reconnect и отсутствие перезапроса посторонних линий.
