# Поиск по готовому списку фильтра — 22 октября 2026

**Результат: меньше SQL, заметное ускорение поиска не подтверждено.** Только сварочный журнал. Без агентов, коммита, push и production. Схема, возможности фильтра, задержка ввода 60 мс и ограничения кэша не менялись.

Выделена общая проверка доступа и актуальности `journalReadIdentity`. Фильтры используют её без загрузки двух настроек и построения SQL условий строк, которые им не нужны. Полное построение списка по-прежнему загружает необходимые ему настройки; чтение строк журнала использует прежнюю полную подготовку. Проверки прав, версии до/после диспетчера, актуальности диспетчера и версии перед выдачей сохранены; ключ кэша с публикацией задач сохранён.

## Сравнение

Одинаковые production-сборки по окружению, Chrome 155.0.8059.85, обычный CPU, DPR 2, 200000 уникальных значений, локальный PostgreSQL с `/dev/shm` 1 ГиБ. Серии: до → после → повтор после. Каждая содержит 5 открытий разных ключей одного и того же набора, 30 поисков через интерфейс и 100 прямых RPC. Во время этих замеров другие тесты не выполнялись.

| Показатель | До | После / повтор |
| --- | ---: | ---: |
| Открытие, медиана | 1178 мс | 1192 / 1190 мс |
| Ввод → результат в DOM, медиана | 154,55 мс | 153,95 / 153,75 мс |
| Прямой RPC поиска, медиана | 56,59 мс | 55,26 / 56,22 мс |
| SQL на поиск | 7 | 5 |
| SQL на первое открытие | 8 | 6 |

За 20 поисков: 140–142 → 100–102 SQL; дополнительные два запроса — периодическая общая проверка готовности сервера. Новых пересчётов диспетчера в этих сериях нет. SQL на поиск сокращены на 29%; различия времени малы, открытие колеблется около 1,18–1,19 с. Заметного ухудшения в этих сериях не выявлено; это не статистическая гарантия для других компьютеров или сети. Стабильного ускорения интерфейса тоже нет, компромисс серверного поиска остаётся.

Время интерфейса измерено от события ввода/клика до появления результата через MutationObserver, без задержки опроса Playwright; это не время физической отрисовки экрана. Ранние цифры открытия 1,45 с включали ожидание автотеста и напрямую с новой методикой не сравниваются. Прямой RPC включает транспорт и десериализацию, а не только серверный CPU.

## Проверки

Полный unit-набор: 625 файлов, **6335 прошли**, 2 опциональных пропущены. Typecheck приложения и E2E, production build и 158 RPC manifest прошли. Покрыты отзыв доступа, устаревшая версия, изменение версии во время проверки, смена публикации задач, истечение кэша, отдельные области поиска, форматированные числовые значения и сохранение подготовки реальных строк.

На 200000 стыков два API-сценария прошли: точные диапазоны/копирование/выбор, обновление вариантов и количеств после изменения стыка, WDI, отказ старой версии, полные фильтры и экспорт. В первом расширенном прогоне новый тест ошибочно сравнивал строку `2` со штатной десятичной `2.000`; проверка исправлена на числовое значение и точные количества. После этого сбоя следующий тест при перезапуске worker получил тайм-аут 60 с. Отдельный чистый повтор обоих прошёл (1,5 мин + 41,9 с); тайм-аут не воспроизведён. Времена того первого API-прогона под параллельным unit-набором не использованы для сравнения производительности.

Подробные логи, включая неудачные диагностические прогоны, и контрольные суммы исходников: `../welding-journal-local-measurements/2026-10-22-filter-cache/` относительно корня проекта. Полный precommit E2E не повторялся: затронута только серверная подготовка журнала, выполнены проверки этой границы. Предыдущая полная проверка описана в [отчёте очистки](precommit-audit-2026-10-22-cleanup.md).

Дополнительно **5/5 WebKit**: даты и временные значения, фокус/выбор фильтра, смена строк и частичный выбор вложенных групп. Установленный Safari отдельно не запускался. Тестовые данные использовали только одноразовую локальную БД; по окончании она удалена. Интерфейс и правила не менялись, поэтому новая инструкция в пользовательском руководстве не требуется.
