## Ограничения нового чата

Никакой реализации, нового аудита/нагрузки, миграций, commit/push/deploy до нового прямого поручения. Не переключать ветку, не создавать worktree, не делать reset/stash, не удалять рабочие данные/артефакты; сохранить две незакоммиченные правки передачи и сервер 3000. Не архивировать предыдущий чат и не отправлять ему команды. Модель/reasoning не менять. Агенты по умолчанию не используются: перед делегированием нужна конкретная польза и новое согласие; разрешение двух агентов относилось к завершённому аудиту.

При отдельно разрешённой реализации **локальные миграции на main уже имеют постоянное разрешение**: проверить точные локальные host/db, сохранить данные; schema → `pnpm db:generate` → просмотр → `pnpm db:migrate`. SQL вручную не писать, повторного согласия только на проверенную локальную миграцию не требовать. Fixtures/load — только отдельная проверенная пустая локальная БД с владением runner, никогда рабочая; не запускать два runner на одной БД. Это исключение не поручает миграцию при чтении передачи.

Production: Selectel, `welding_journal`, приватная сеть; старый Yandex URL в `.env` устарел. Перед отдельно разрешённой операцией сверять адрес с Coolify runtime. Read-only viewing не разрешает тесты, пересчёты и скрытые записи. Push в main может вызвать autodeploy и сейчас прямо запрещён. [Справочник production](production-links.md) не является разрешением на действия. Текущий production при передаче не проверялся; сведения последнего известного выпуска не подменяют актуальную сверку перед будущим выпуском.

Новые правила требуют обновления встроенного руководства, изменения диспетчера — версии расчёта и регрессий. При отдельно порученной работе над уже реализованной авторизацией применять официальный Better Auth MCP/skills с установленной версией из lockfile; организации/MFA автоматически не добавлять.
