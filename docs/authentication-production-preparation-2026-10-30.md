## Проверено без изменения сервера

- DNS домена приложения указывает на `176.53.227.78`; в Coolify домен с HTTPS и перенаправлением HTTP → HTTPS, порт приложения 3000. Дополнительный существующий адрес sslip.io не менялся.
- Проверка TLS с локального компьютера подтверждает доверенный сертификат для точного домена, срок до 13.01.2027. Использовалось только TLS-рукопожатие, без HTTP-запроса к приложению.
- MX `yums.ru` — `mx.yandex.net`, SPF — `redirect=_spf.yandex.net`; опубликован DKIM по `mail._domainkey.yums.ru`. TXT-ответ для `_dmarc.yums.ru` пустой. DNS не менялся.
- Параметры сверены с текущими `src/server/auth.ts` и `src/server/auth-mail.ts`: HTTPS, точный trusted origin, защищённые cookie, SMTP с неявным TLS на 465.
- В Coolify проверен healthcheck: `GET /health/live`, порт 3000, ожидаются HTTP 200 и `{"alive":true}`. Он позволяет новой версии запуститься до подготовки БД и активации владельца. Команды pre-/post-deployment пустые: автоматического выполнения миграций сейчас нет.
- Прочитана конфигурация Traefik v3.7: порты 80/443, без `forwardedHeaders.insecure` и `trustedIPs`; Coolify сообщает о совпадении сохранённой и работающей конфигурации. У приложения нет host port mapping, маршрут HTTPS ведёт на внутренний 3000, middleware — gzip и перенаправление HTTP → HTTPS. По [документации Traefik 3.7](https://doc.traefik.io/traefik/v3.7/reference/install-configuration/entrypoints/#forwarded-headers) доверие произвольным forwarded-заголовкам по умолчанию выключено. Сквозная проверка подменённого IP на production не выполнялась; `AUTH_TRUST_PROXY=false` оставлен без изменений. Это сохраняет общий лимит входа 60 попыток/минуту плюс 8 попыток/минуту на почту; включать доверие заголовку без отдельной проверки не требуется для запуска авторизации.
- Использованы официальные skills Better Auth и MCP; установленная версия — 1.7.14, индекс относит `/docs` к 1.7. Источники: [cookie Better Auth](https://better-auth.com/docs/concepts/cookies), [SMTP Яндекс](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others), [переменные Coolify](https://coolify.io/docs/applications/configuration/environment-variables).

## Порядок будущего выпуска и оставшиеся проверки

1. Перед выпуском проверить чистоту ветки `main`. Операторская удалённая миграция после публикации требует совпадения HEAD с `origin/main`. Код уже закоммичен; дополнительные проверки не потребовали правок приложения. Локальный коммит двух итоговых отчётов отдельно разрешён пользователем; разрешения на push пока нет.
2. Согласовать окно без рабочих изменений; пользователь делает свежую копию БД до push. Проверить завершение и доступность копии, учесть сохранность постоянного хранилища шаблонов. Сам резерв ещё не получен этой подготовкой.
3. Только после отдельного разрешения выполнить push и дождаться автодеплоя **точного релизного коммита**. Проверить healthcheck и завершение старых контейнеров/пишущих заданий. Новая версия будет показывать страницу обновления, пока БД не подготовлена.
4. После завершённого деплоя и подтверждённой паузы записи выполнить штатную `pnpm db:remote-migration` с подтверждениями резерва, окна обслуживания и развёрнутого релиза. Не выполнять миграции раньше публикации/деплоя и не запускать их вручную через прямой Drizzle. Проверить точные host/database и результат готовности.
5. Подготовить настоящего владельца операторским скриптом из соответствующего checkout с зависимостями и защищёнными настройками SMTP/БД; runtime-образ не содержит исходные операторские скрипты. Проверить доставку письма с production, дать пользователю задать пароль, проверить вход и права; затем приглашать сотрудников.

Реальная доставка, доступность SMTP именно с сервера и cookie на production остаются непроверенными. До разрешённого выпуска нельзя гарантировать работу внешних сервисов и облачного деплоя; локальные проверки подтвердили поведение приложения и обновления БД.
