# План ускорения расчётных фильтров отчётов

Дата: 19 октября 2026. **План принят пользователем; реализация и согласованные проверки завершены.** [Результат и замеры](report-derived-filters-optimization-2026-10-19.md).

Цель — ускорить фильтры ЛНК, ПСТО, сварочного журнала и выявленные аналогичные пути других таблиц, сохранив состав строк, значения, сортировку, счётчики и все рабочие действия. Основное изменение: база данных отбирает подходящие записи до загрузки страницы в серверное приложение. Подробности, необходимые для отображения и действий, подгружаются пакетно для этой страницы.

Зафиксированный пример: глобальный фильтр ЛНК «Результат РК → ремонт» на локальной базе 200000 стыков занял около **6,1 с**, выполнил 26 SQL-запросов и прочитал в приложение 200000 расчётных строк ради страницы из 100. Это прежний замер конкретного сценария, а не время всех фильтров. Бейджики и AG Grid не являются причиной этого чтения. Источник: [отчёт переноса ЛНК](lnk-ag-grid-implementation-2026-10-19.md).

Реализация разрешена пользователем 19 октября 2026: без агентов, коммита, push, деплоя и production-операций; в текущем checkout и ветке, с сохранением прежних незакоммиченных изменений. Эта задача не запускает отложенный системный аудит, план ограничений печати или репетицию production-резерва.

## Область исправления

| Область | Что обнаружено в текущем коде | Направление работы |
| --- | --- | --- |
| ЛНК | `listDerivedReportRowIds` читает всю область обычных фильтров, присоединяет контроль и историю, рассчитывает строки и возвращает массив ID. Аналогичный расчёт есть в списках значений. | Все доступные поля классифицировать; основной НК ВИК/РК/УЗК/ПВК, заявки, даты, заключения, основания, НК до ТО, схема РК и описания дефектов разобрать по зависимостям. Устранить общий массовый расчёт там, где достаточно исходного поля или SQL-выражения. |
| ПСТО и ТВМТ | Общая запасная ветка такая же. При этом поля текущего цикла уже обслуживает `psto-report-current-values.ts`. | Сохранить и переиспользовать готовый SQL. Проверить оставшиеся поля, включая сводку циклов, основания, поля НК и комбинации с расчётными фильтрами. |
| Сварочный журнал | `journal-filter-source.ts` читает расчётную проекцию всей области для НК до ТО, оснований контроля, схемы РК и WDI в системном режиме. Списки значений имеют дополнительные широкие ветки. | Перевести эти семейства на отбор в БД, используя существующие зависимости. Для WDI проверить повторное использование `current-wdi-sql.ts`, уже применяемого в документах. |
| Реестры документов | Поиск, фильтры, группы и порции уже формируются SQL через `document-history-grid.ts`; идентичная проблема массовой сборки строк в приложении здесь пока не установлена. | Проверить исходные запросы системных и пользовательских документов, WDI, связи, списки значений и общие фильтры документов в отчётах. Исправлять подтверждённые лишние чтения, сохраняя серверную группировку. |
| Программа линий, вложенные таблицы и окна | Есть отдельные расчёты полных линий и кэш обзоров. Полная линия нужна для правильных квот; фильтры отображения не всегда являются серверными. | Проверить загрузку обзоров, списки/клейма/стыки/назначения. Сократить повторные расчёты и лишние зависимости, если они выявлены. Не рассчитывать квоту по отфильтрованной части линии и не переносить клиентские фильтры на сервер автоматически. |

Проверить каждое семейство не только в странице таблицы, но и в списках значений фильтра, общих итогах, доступности заявок, полном выводе и связанных отборах для массового заполнения/шаблонов замены. Специализированные отчёты сохраняют собственный состав и правила. Общие итоги сервера и итоги групп загруженных строк — разные области; их нельзя объединять ради ускорения.

## Способ реализации

1. **Общий источник условий отбора.** В небольших профильных модулях описать SQL-значение или условие для каждой поддержанной группы полей, учитывая вид отчёта, настройки и необходимые связи. Страница, счётчик, список значений и вывод используют эти же выражения. Не создавать отдельный универсальный движок фильтров и не переписывать уже работающие SQL-пути.
2. **Исходные поля без лишнего расчёта.** Проверить поля, попадающие в запасную ветку только потому, что их нет в списке SQL-полей. Переносить их в прямой отбор после проверки фактической семантики: даты/заключения основного этапа, текущего цикла и НК до ТО нельзя считать взаимозаменяемыми.
3. **Расчётные значения в SQL.** Для состояний использовать проверенные `CASE`, `EXISTS`, пакетные соединения и выбор актуальной записи истории. Сначала повторно использовать текущие SQL-помощники ПСТО, доступности контроля, результатов, WDI и документов. Историю выбирать однозначно; несколько записей контроля не должны размножать стык. Измерить планы запросов: один SQL-запрос с дорогим подзапросом на каждый стык тоже может быть медленным.
4. **Порция после полного отбора.** Применять все условия до `LIMIT/OFFSET`, сохранять сортировку и её устойчивый порядок при равных значениях. Получать страницу/ID страницы непосредственно из БД, затем пакетно её данные, документы и необходимый контекст цепей, включая корни вне страницы. Не переносить в приложение все найденные ID для последующего `slice` или огромного `IN`.
5. **Зависимости по необходимости.** Не подключать дубль, НК до ТО, циклы, документы или пересчёт итоговых статусов, если запрошенные поля их не используют. Отдельно разобрать `loadCurrentFinalStatusRowsContext`: сейчас он читает все неофициальные записи. Использовать актуальный существующий индекс статусов там, где он даёт нужный ответ; иначе ограничить контекст действительно связанными цепями и тёзками, сохраняя их полный состав. Не заменять его заведомо устаревшим сохранённым статусом.
6. **Итоги и списки значений.** Считать `COUNT`, допустимые суммы и варианты значений в БД по тому же отбору. В списке значений исключать только собственный фильтр столбца, сохраняя остальные ограничения и поиск по действующему контракту. Различать пустое значение, отсутствие строки истории и служебную подпись. Большое число уникальных значений — отдельная стоимость ответа; не вводить скрытое усечение.
7. **Кэш как дополнение.** Сохранить объединение одинаковых одновременных расчётов, проверку ревизии данных и защиту публикации от устаревшего результата. Проверить ключи с учётом настроек и публикации диспетчера. Не делать ускорение зависимым только от прогрева кэша и не запускать полный пересчёт диспетчера при любом фильтре.

Полный экспорт по назначению читает все выбранные записи; здесь задача — убрать повторный расчёт и загрузку посторонних данных, сохранить полный результат, снимок, порядок и действующие ограничения. Ожидать расход памяти как у страницы из 100 строк от полного Excel некорректно. Ограничения печати этой задачей не меняются.

**Основной вариант — без нового сохраняемого расчётного индекса.** Простые индексы БД добавлять только после анализа планов запросов и измерения пользы/цены записи. Новый сохраняемый индекс сложных значений рассматривать отдельно, только если SQL не достигает приемлемого результата. До такого решения описать конкретные поля, размер, начальное заполнение, все источники изменений, атомарное обновление, восстановление и стоимость сохранения. Это резервный вариант, а не заранее выбранная архитектура.

Для сложных текстовых проекций, например разборов описания дефектов РК, сначала проверить возможность точного SQL-вычисления и безопасного предварительного отбора. Временная обработка ограниченными пакетами может уменьшить память, но не считается полным исправлением, если каждый фильтр продолжает обходить все 200000 строк. Каждый оставшийся такой путь должен получить явное решение; нельзя объявить задачу завершённой, просто спрятав его в запасную ветку.

## Сохранение смысла фильтров и рабочих правил

Перед заменой создать таблицу соответствия «вид отчёта → поле → исходный факт → отображаемое значение → значение фильтра/списка → сортировка». Текущий код не везде использует один и тот же преобразователь для ячейки и фильтра. Не считать их тождественными заранее и не менять смысл отбора под видом ускорения. Подтверждённое расхождение описать отдельно; если исправление меняет рабочий результат и требование неоднозначно, согласовать его до изменения.

Проверить на небольших наборах с независимо заданным ожидаемым результатом:

- ВИК/РК/УЗК/ПВК: отсутствие назначения, активное/отменённое назначение, пустой результат, ожидание заявки/НК, годен/ремонт/вырез, сохранённый исторический результат после отмены, «нет потребности», брак другого метода, дубля и НК до ТО. Подпись ожидания сама по себе не доказывает начало работ.
- НК до ТО и основной этап: независимость результатов, заявок, дат, заключений и специалистов; ранний основной НК при соответствующей настройке; старые неполные документы, отсутствие записи этапа, разные истории стыков на одной линии.
- ПСТО/ТВМТ: первичный и повторные циклы, пустой/частичный последний повтор, отмена и возобновление, фактически выполненная история. Пустое значение текущего повтора не должно незаметно заменяться значением старого цикла.
- Итоговый статус и цепи: официальные/неофициальные тёзки, исправленный и оставшийся брак, R/W/Y, корень вне страницы, перенос линии, удаление допустимой записи с восстановлением официальности и будущим продолжением. Защиты предшественников и зависимостей сохраняются.
- WDI: ручной, формульный и табличный режимы; правила выбора диаметра/толщины, равные диаметры, неполные размеры, границы таблицы, пустая ячейка, округление, изменение настроек. Схема РК: автоматическая и подтверждённая, старые описания, несколько координат/дефектов.
- Сам отбор: точное значение и текстовый поиск, несколько значений, пусто, регистр/пробелы, специальные символы, числовые и датовые представления, документы с несколькими значениями, скрытые ограничения ID/цепей/диспетчера/клейм. Комбинации должны сохранять действующие правила AND/OR и экранирования.

Сравнение со старым путём полезно для обнаружения расхождений, но существующие тесты и код не являются единственным доказательством правила. Расчётные проекции предназначены для чтения: ими нельзя перезаписывать фактические поля или подменять серверную проверку сохранения. Массовое заполнение и замена сохраняют версии строк, повторную проверку конечной записи, атомарность и права.

## Порядок работы

1. **Зафиксировать исходное состояние.** Сохранить отдельный снимок текущего diff и список доступных полей/путей, не включая прежние правки в новое изменение. Для каждой таблицы отметить серверную и клиентскую границы, готовый SQL, запасной расчёт и легитимный полный расчёт. На изолированной базе снять воспроизводимый исходный профиль; 6,1 с использовать как исторический ориентир.
2. **Сформировать проверяемый контракт.** Добавить маленькие смысловые fixtures и проверки равнозначности БД и ожидаемых значений; проверить вызывающие пути, включая шаблоны замены. Зафиксировать нормализацию, области итогов/списков и устойчивую сортировку до оптимизации.
3. **Ускорить основной ЛНК.** Перевести все четыре метода и прямые поля, затем страницу, списки, счётчики и вывод. Закрыть глобальный сценарий РК и его аналоги. Проверить комбинацию нового SQL-поля с ещё не перенесённым полем, чтобы она не теряла условие и не возвращала весь прежний расчёт без необходимости.
4. **Перенести общие расчётные семейства.** НК до ТО, основания, WDI, схема РК и текстовые проекции; ПСТО/ТВМТ с повторным использованием готового текущего цикла. Обработать все выявленные поля, а не только показавшие большой тайминг в одном замере.
5. **Проверить соседние таблицы и актуальность.** Документы, программа линий и вложенные окна: устранить подтверждённый аналогичный лишний расчёт. Проверить изменение результатов, заявок, дат, циклов, настроек, официальности, документов, переносы и удаления через одиночные/массовые операции и импорт. После сохранения фильтр и список значений обновляются; старый запрос не перекрывает более новый. Сохранить существующие границы снимков, при необходимости объединить зависимые чтения одного ответа в согласованный снимок без длительных блокировок записи.
6. **Завершить проверку и убрать старые пути.** Удалить недостижимые ветки, лишние проекции и дубли после покрытия их замен. Провести проверки ниже. Представить сравнительные результаты по семействам полей, оставшиеся ограничения и сведения о миграциях. Реализацию принимать по всему согласованному объёму, а не по одному ускоренному РК.

## Проверки и критерии приёмки

**Корректность.** Для каждого затронутого семейства совпадают ID и порядок страницы, следующие страницы, `hasMore`, общий счётчик, варианты/количества списка значений и полный вывод согласно их собственным областям. Проверить отсутствие повторов/пропусков, пустой результат и фильтр, совпадающий со всеми строками. Пройти четыре согласованных сценария назначения/возобновления/отмены ПСТО и переноса между линиями, включая snapshots специалистов и конфликтующие объединения, когда они меняют значения фильтров.

**Актуальность.** Холодный и прогретый кэш; изменение фактов и настроек при открытом отчёте; несколько одинаковых и разных запросов одновременно; устаревший клиент, отмена/повтор и транзакционный откат. Фильтр по итоговому статусу сохраняет проверку свежести индекса. Ошибка расчёта не превращается в «строк нет». Массовые операции повторно проверяют выбранные записи независимо от кэша отображения.

**Масштаб.** Использовать только отдельную проверенную пустую локальную БД и временное хранилище. Сравнить объёмы 1000, 10000 и 200000 стыков; на 200000 — разные линии и профиль с одной большой линией, история нескольких методов/этапов/циклов, редкие/частые значения и длинные текстовые поля. Порции 100/1000, поздняя страница, общая и узкая область, обычный/производный/смешанный фильтр, списки значений, итоги и полный вывод в действующих пределах.

Измерять количество RPC/SQL, строки и объём **из БД в приложение**, размер ответа браузеру, CPU/память серверного процесса, планы SQL с буферами и время. Текущую метрику широкого чтения дополнить узкими выборками: массив 200000 ID тоже должен быть виден в отчёте. Для основных медленных сценариев минимум три холодных повтора; для повторных и смешанных запросов — серия, достаточная для медианы и p95. Отдельно пять одновременных клиентов, включая сохранение во время чтения; проверять отсутствие повторного массового расчёта и роста очереди запросов. Условия и ресурсы до/после одинаковые и записаны.

Обязательные условия результата:

- Для перенесённого постраничного пути приложение не собирает все стыки или все совпавшие ID. Объём загрузки карточек определяется страницей и необходимыми связанными данными; связи читаются пакетно. Списки/итоги возвращают агрегаты, а не исходные карточки.
- Нет N+1, веерных запросов по строкам, рефетчей крупных неактивных отчётов и полного перестроения диспетчера из-за обычного выбора фильтра. Сохранение не получает новый массовый пересчёт ради ускорения чтения.
- Холодные медленные сценарии заметно ускорены по повторным замерам; обычные страницы, сохранения и существующие SQL-фильтры не имеют устойчивой регрессии. Для исходного глобального РК рабочий ориентир — как минимум двукратное ускорение относительно повторно измеренного исходного пути. Это цель проверки, не обещание конкретного production-времени; недостижение требует разбора и явного решения до приёмки.
- Чтение многих строк внутри БД для точного `COUNT`, `DISTINCT`, сложного условия или полного экспорта допустимо, если обосновано и измерено. Обещание «любой фильтр всегда читает только 100 строк в БД» было бы неверным.
- Сохраняются группировки, выделение/суммы/копирование, обязательные столбцы, настройка вида, прокрутка и рабочие формы. Проверить загрузку/смену фильтра, быстрые переключения и поздние ответы, восстановление вида, выбор вне текущего отбора, фокус и открытие документов. От прокрутки/выделения не появляются посторонние RPC.

Проверки реализации: типы приложения и E2E, полный unit-набор, production-сборка с проверкой RPC, целевые новые проверки БД и **полный пользовательский E2E-набор**, поскольку меняется общий отбор нескольких рабочих разделов. Нагрузочные профили запускать отдельно и перечислить фактически выполненные; старые успешные прогоны не засчитывать за новый код. Это приёмка данной задачи, не весь отложенный системный аудит проекта.

Базовый вариант не требует изменения схемы. При обоснованном добавлении SQL-индексов: сначала Drizzle schema, затем `pnpm db:generate`, просмотр полученной миграции и локальное применение на `main` после проверки адреса/имени БД. Миграции вручную не писать, production не затрагивать. Руководство менять, если появится согласованное пользовательское изменение; техническую оптимизацию с полностью прежним поведением описать в отчёте реализации.

## Модель для реализации

Для этой задачи рекомендуется **GPT-6 Astra, «Очень высокое»**: основная сложность в равнозначности нескольких представлений результата, истории и конкурентных изменений. План уменьшает неопределённость, но не делает перенос этих условий механическим.

Более экономичный вариант — GPT-6.1 Sol, «Очень высокое», для реализации зафиксированных частей с проверкой архитектуры и бизнес-эквивалентности на Astra перед завершением. При обнаружении неоднозначной семантики или необходимости нового сохраняемого индекса перейти на Astra до выбора решения. Равенство качества моделей на этом проекте не измерено; такую гарантию давать нельзя. Запуск тестов сам по себе не требует смены модели, она полезна для оценки покрытия и разбора расхождений.

Это рекомендация для данного проекта. [Официальное описание моделей OpenAI](https://learn.chatgpt.com/docs/models) относит Astra к наиболее сложным задачам, а GPT-6.1 Sol — к длительной работе при важности стоимости. Обе модели работают без агентов в рамках ограничений проекта.

## Уточнения при реализации

- Пользователь подтвердил: «Да, сделать одинаковый порядок». Без явной сортировки расчётные фильтры используют тот же порядок страниц, что обычные фильтры. Сортировка по заголовку сохраняется; при полном равенстве добавлен стабильный ID. Изменение описывается в руководстве.
- После первого сравнения SQL ускорил холодный РК примерно с 6,6 с до 0,17 с, но выявлена потеря прежнего выигрыша прогретого кэша. Поэтому кэшируется только ограниченный набор ID и версий **одной страницы**, с разными ключами страницы/сортировки и общей защитой ревизии. Полные карточки повторно читаются и проверяются по версии. Общего массива всех найденных ID больше нет. Для WDI и схемы РК ключ дополнительно содержит короткий отпечаток фактически прочитанных настроек: даже при их конкурентном изменении старая формула не публикуется под новым ключом. Полный вывод использует прямой SQL. Окончательные парные замеры выполнены после этой доработки, включая прогретые WDI и настроенную схему РК; результаты приведены в отчёте реализации.
- Действующий предварительный предел полного вывода сохранён в прежней области исходных фильтров. Его расширение за счёт расчётного фильтра в эту оптимизацию не включено; отдельный план ограничений вывода/печати не запускается.


### Контракт значений для реализации

| Поля / область | Источник отбора и списка значений | Сохранённое различие с отображением |
| --- | --- | --- |
| Основные результаты ВИК/РК/УЗК/ПВК в ЛНК и ПСТО | Исходный результат + подпись отменённого назначения | Не подставлять дополнительные подписи ожидания/«нет потребности», которые ячейка рассчитывает позднее. |
| Заявки, даты, заключения основного НК | Соответствующее исходное поле | Даты основного этапа не заменяются датами до ТО. |
| НК до ТО | Единственная запись соответствующего метода; отмена, брак другого назначенного метода, разбор координат/дефектов РК | Сохраняется прежняя проекция полей, присоединяемая до текущей политики этапа. |
| ПСТО / ТВМТ | Существующий выбор текущего первичного/повторного цикла и его SQL-значения; сводка использует тот же выбор | Пустой текущий повтор не наследует поле из первичного; факты карточки не заменяются подписью. |
| Основания | ВИК/РК/УЗК/ПВК с непустыми основаниями и прежними разделителями | Область ПСТО для общей сводки оснований остаётся пустой, отдельное основание ПСТО сохраняется. |
| WDI / схема РК | Текущие настройки; готовая формула/таблица WDI; эффективный и подтверждённый диаметры, упорядоченные координаты | Ручной WDI сохраняет исходную SQL-семантику; системный WDI — числовое представление прежнего расчёта. |
| Итоговый статус, документы, задачи и скрытые ограничения | Существующий индекс/SQL-связи; барьер свежести статусов и версия публикации задач | Многозначность документов, ожидание послойного контроля и пустые значения не сводятся к одному текстовому полю. |

Обычные SQL-фильтры сохраняют свою нормализацию и ILIKE. Поля, прежде обрабатывавшиеся JavaScript, сохраняют буквальное значение `%`, `_`, обратной косой черты, точный поиск и регистр вариантов выбора. Список исключает только собственный фильтр столбца. Контрольные проверки SQL сравнивают семейства со старыми функциями и отдельно заданными фактическими ожиданиями.
