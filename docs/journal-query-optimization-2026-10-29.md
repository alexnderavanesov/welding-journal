# Фильтрация, сортировка и группировка — 29.10.2026

Локальная реализация завершена по отдельному поручению пользователя. Коммит, push и изменения production не разрешены и не выполнялись. Предыдущие незакоммиченные улучшения сохранены; исходная точка этого сравнения уже включает [завершение плавного обновления](journal-refresh-completion-2026-10-29.md).

Последующее решение пользователя от 29.10.2026: готовые изменения, включая сортировку «Стыка», оставить; весь дальнейший этап отложить ради авторизации. [Отложенный план углубленной оптимизации](journal-deep-optimization-deferred-plan-2026-10-29.md) сохраняет фильтрацию, группировку и ограниченный набор сортировок, включая «Шифр». Реализация этого плана не начата.

Основной измеренный выигрыш — сортировка номера стыка и повторное раскрытие групп. Обычная фильтрация и первое построение крупных групп не получили сопоставимого ускорения. Все результаты ниже локальные; скорость production не проверялась.

## Что изменилось

- Для естественного порядка номера стыка (`F2` перед `F10`) добавлены два индекса: возрастание и убывание. Общий SQL-конструктор сохраняет прежние числовые части, пустые значения и дополнительные ключи порядка. Индексы на каждый столбец и сочетание группировок не создаются.
- Первые страницы большой выборки получают ограниченный набор кандидатов до загрузки полных карточек. Узкие выборки и глубокая прокрутка используют прежний запрос. Это выбор алгоритма, а не ограничение количества доступных строк.
- Очень длинные исторические номера и линии остаются доступными для записи и сортировки: они исключены только из составного индекса и участвуют в отдельной ветке того же запроса. Новый лимит ввода не вводится.
- Повторное раскрытие недавно просмотренной конечной группы использует строки той же версии без повторного запроса блока. Дополнительный кеш ограничен 500 карточками / 16 блоками и очищается при смене выборки, уведомлении, сохранении, явном обновлении и ошибке версии. Ответ, начавшийся до очистки, не может заполнить кеш заново.
- При раскрытии текстовых групп сравнивается исходный столбец, что позволяет использовать существующие индексы. Числовые и вычисляемые поля сохраняют прежние правила. Из расчёта итогов исключены ненужный разбор исторических имён и сортировка всех дат.
- Нижняя сводка повторно использует уже посчитанное количество строк только для той же выборки и версии. Проверка живой версии выполняется внутри расчёта сводки; устаревший счётчик не публикуется под новой версией.

Справка внутри журнала, ЛНК и ПСТО обновлена. Бизнес-правила, актуальное открытие карточки и проверки конкурирующего сохранения не менялись.

## Подтверждённые измерения

Локальные production-сборки, три повторения, одинаковые фикстуры внутри каждой пары до/после. Матрица RPC и прежняя UI-фикстура используют разные наборы данных и отборы; их абсолютные времена нельзя смешивать. Значения — медианы; время RPC и время готовности интерфейса измеряются отдельно. В строках раскрытия считаются RPC загрузки блоков; независимые запросы итогов выделения могут завершаться параллельно. Это не гарантия времени на production.

Обычная фильтрация, сортировка даты и первое раскрытие группы не получили равномерного заметного ускорения. Например, RPC текстового фильтра на 200000: 236 → 241 мс; большой группы по проекту: 1714 → 1815 мс. В Safari быстрый поиск: 494 → 490 мс. В контролируемом UI-сценарии Chrome сводка после поиска ускорилась с 173 до 103 мс, но общее ожидание поиска осталось сопоставимым: 944 → 975 мс. Изолированный расчёт итогов 200000 обычных строк ускорился с 453 до 357 мс, но это лишь часть общего ожидания большой группы. Повторные раскрытия ускоряются значительно сильнее первых.

Время Chrome включает ожидания браузерного теста с дискретными проверками готовности; это не покадровый FPS. Поэтому для первой/вложенной группировки показатели UI 877 → 407 и 1363 → 849 мс не следует трактовать как такое же ускорение сервера: соответствующие RPC изменились лишь с 314 до 306 и с 834 до 791 мс. Для сортировки реальный RPC-выигрыш подтверждён: 467 → 108 мс.

Полная проверка порядка включает границы страниц, обе сортировки, пустые значения, регистр, ремонты/катушки, длинные имена и строки вне индекса. Число SQL-команд в матрице остаётся ограниченным; сохранение выделения при сворачивании и раскрытии проверено в Chrome и установленном Safari.

## Стоимость и схема

Сгенерированная через Drizzle миграция `0052_lying_peter_quill.sql` содержит только два `CREATE INDEX`. Дополнительный индекс линии отклонён: устойчивой пользы не показал. На измеренных фикстурах два оставшихся индекса заняли около 3,3 МиБ при 9000 строках и 105 МиБ при 200000. В изолированных пакетах по 1000 строк медианы SQL: вставка 23 → 33 мс, изменение изометрии 31 → 42 мс, номера стыка 27 → 41 мс. Это стоимость пакетных SQL-записей, а не время пользовательского сохранения.

Миграция применена на `main` только к проверенной `localhost:5432/welding_tracker`. Контрольная сумма всех 77 рабочих стыков и количества связанных записей до/после совпали. Данные не заменялись тестовыми. Для будущего выпуска потребуется эта миграция; на production она не применялась.
