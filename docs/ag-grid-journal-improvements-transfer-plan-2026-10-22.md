# Перенос улучшений сварочного журнала на остальные AG Grid-таблицы

**Последующее прямое поручение 22.10: реализация разрешена и начата.** Без агентов, в порядке ЛНК → ПСТО → документы → все таблицы программы, включая вложенные и модальные. Для документов согласованы полный выбор, диапазоны и копирование незагруженных записей. В программе сохранять текущие элементы и границы действий; если галочек нет, новые не добавлять. Сохранить черновики и соответствующего владельца прокрутки. Без коммита, push и production-действий. Это поручение заменяет ожидание команды в первоначальной записи ниже; системный аудит и отложенные профили не запускаются.

**Исторический статус при подготовке плана: перенос ещё не был начат.** Последующее разрешение приведено выше; текущая реализация и проверки описаны в [отчёте переноса](ag-grid-transfer-2026-10-22.md). План фиксирует положительные согласованные результаты журнала для всех существующих AG Grid-таблиц, включая вложенные и модальные. Общий код для Chrome/Safari, сохранение возможностей и отсутствие подтверждённого ухудшения — обязательные условия.

Исходная граница: последний опубликованный по истории чата код `3bac76fa`; накопленный результат журнала — локальный коммит **`fcc9ba391973b009c012b4aa9bc2e163caa5df22`**, без push. Сверены текущий код, [актуальное поведение](ag-grid-journal-server-2026-10-21.md), [итоговая проверка](precommit-audit-2026-10-22-cleanup.md), [последняя оптимизация фильтра](journal-filter-cache-2026-10-22.md), ключевые разделы сохранённой подробной истории и замечания пользователя. Это не новая приёмка браузеров и не системный аудит.

## 1. Что действительно изменилось после push

Журнал перестал группировать только вручную догруженные страницы. Он показывает одну непрерывную виртуализированную таблицу, а сервер обеспечивает полный отбор, группировку, выбор и диапазоны. **Все карточки из БД одновременно в браузер не загружаются.** Изменились интеграция прокрутки, загрузка, клавиатура и стоимость видимых ячеек; бизнес-правила стыков не переписывались. Небольшие изменения общих компонентов сохранены, но новый режим включён только для `weldingJournal`.

ЛНК, ПСТО, документы и программа линий **уже были на AG Grid до этой задачи**. Их не нужно переносить с нуля. Требуется адаптировать последние улучшения, сохранив их собственные данные, области выбора, действия и формулы. Исторические планы со словами «группировка загруженных строк» не описывают новый журнал, но пока могут правильно описывать другой отчёт.

После катушки исходник исключается, стороны считаются отдельно. Ошибка истории имеет приоритет, заменённый предшественник не делает исправленную цепочку браком. Фильтр сначала отбирает записи, итог считается по оставшемуся набору без ложной «полной годности». Профильные результаты ЛНК и ПСТО/ТВМТ имеют собственную семантику — использовать их сумматоры, не копировать общий статус журнала.

## 5. Предлагаемая последовательность после новой команды

1. **Матрица переноса и исходные замеры.** Для каждого семейства сопоставить U01–U18 и технические механизмы с текущим поведением. Согласовать порядок ЛНК/ПСТО и границы полного выбора/диапазонов документов, действий и контейнеров вложенных таблиц. Сохранить `fcc9ba39` как эталон журнала; не откатывать checkout ради сравнения. Проверить локальные процессы и изоляцию тестов.
2. **Общие небольшие части.** Выделять только реально общий механизм; переносить подтверждённые лёгкие ячейки, состояние загрузки, взаимодействие/фокус и измеримые расходы по одному. После каждого изменения проверять журнал и всех потребителей общей части, не оставлять два расходящихся варианта обработчика.
3. **Первый профиль ЛНК или ПСТО.** Адаптировать серверные страницы/группы/выбор/диапазоны/версию и подготовленную замену, сохранить профильные расчёты/действия. Проверить малые независимые бизнес-контрпримеры, затем 200000 стыков и браузеры; показать пользователю результат, прежде чем тиражировать спорное UX-решение.
4. **Второй профиль; документы; программа.** Распространить общий результат, сохранив различия из раздела 4. Порядок документов и программы уточнить по цене/риску и приоритету пользователя. Не внедрять journal-specific формулы/кэши/скролл во все таблицы механически. Завершённые старые миграции не повторять.
5. **Очистка и итоговая приёмка.** Удалить только заменённые ветви, проверить всех потребителей, обновить пользовательское руководство. Целевые регрессии после этапов; на итоговом общем коде typecheck приложения/E2E, unit, production build/manifest, полный пользовательский E2E и необходимые нагрузочные сценарии изменённых путей. Полный предкоммитный аудит, коммит и дальнейший выпуск — по отдельным поручениям; восемь специальных профилей/системный аудит не запускать под видом переноса.

## 6. Измеренные достижения и пределы доказательств

Исторические сравнения внутри каждого опыта использовали одинаковые условия; они не складываются в общий процент ускорения. Самые полезные ориентиры:

| Что подтверждено | Измерение и оговорка |
| --- | --- |
| Убрано накопление таймеров scroll-партнёра | 350 → 0 после четырёх жестов. Это конкретная регрессия AG Grid 36.2.0. |
| Равномернее быстрый скролл с группой после облегчения ячеек/пересчётов | Обычный CPU: p95 20,0 → 16,8 мс; интервалы >25 мс 22 → 0. Сценарий/данные — в архивной истории, не обещание для всех таблиц. |
| Строки не отстают от нативного движения между событиями JS | Без групп 222/226 отставших кадров → 0/224, с тремя уровнями 182/189 → 0/234. CSS mapping не добавляет инерцию/задержку ввода. |
| Меньше карточек и повторной передачи выбора | 7900 → 1900 карточек после обхода 40 групп на 200000 стыков; heap 137,2 → 129,5 МиБ. Повторный запрос счётчиков после полного выбора 3693987 → 0 байт, первоначальное получение ID остаётся. |
| Меньше невидимой работы при resize; стабильнее фон | Опыт запаса DOM: WebKit p95 45 → 34 мс, Chrome 18,1 → 17,1 мс. Холодный горизонтальный проход Safari со статичным фоном 63 → 26 мс; прогретая медиана 22 → 21. Разные опыты/составы данных. |
| Быстрее подготовленная замена фильтра/сортировки | Ранний опыт на 200000 записей с замедлением **браузерного** CPU ×4: сортировка 1148 → 530 мс, пустые кадры 154/94 → 0/0. Не выдавать за обычный CPU или увеличение серверных ресурсов. |
| Меньше SQL поиска готового фильтра | 7 → 5, первое открытие 8 → 6. Обычный CPU: открытие 1178 → 1192/1190 мс; поиск до DOM 154,55 → 153,95/153,75 мс. Заметного ускорения UI нет; результаты и защиты сохранены. |

**Принятый компромисс закрыт:** пользователь 22.10 оставил гибридный фильтр. Историческое открытие 200000 значений 2,06 → 1,45 с, поиск 33 → 166 мс. Более точная последующая методика DOM исключила задержку опроса автотеста; старые и новые времена открытия напрямую не сравнивать. Не возвращать этот вопрос как неразрешённый и не обещать отсутствие любого компромисса; новый перенос должен сохранять согласованное поведение и измерять свой эффект.

Свежий контроль перед коммитом: Chrome — вертикаль p95 19,6 мс, горизонталь 20,9 мс, resize 18,1–18,3; WebKit — 20 / 30 / 25–26 мс, горизонтальный max 78. Во время прогретых жестов RPC 0. **Safari всё ещё не равен Chrome.** Ранее native Safari 26.6.2 проходил сравнения и клавиатуру; итоговая поздняя проверка всего кода выполнена Chrome/WebKit, не свежим installed Safari. Исторический отдельный прогон Safari подтвердил колесо над ячейками; это не новая проверка каждого физического жеста.

Общий `overscroll-behavior-y: auto; ...: chain` сохраняет прокрутку над ячейками в старом WebKit; при неподдерживаемом `chain` возможна стандартная пружина на краю страницы. Не возвращать корневые `none/contain` вслепую и не перехватывать wheel ради подавления пружины. Общий код проверяет возможности платформы, не название браузера.

## 7. Что не переносить как удачную оптимизацию

- Объединение/повторная отправка PointerEvent при resize: меньше обновлений, но подтверждающий Safari p95 27 → 30 мс и добавленная задержка. **Отклонено**.
- Отмена горизонтального flush: Chrome местами лучше, WebKit хуже/пустые кадры. **Отклонено**.
- CSS contain на строках/ячейках/viewport, отдельные графические слои и замена теней групп: устойчивого выигрыша обоим движкам нет. **Не оставлены**.
- Увеличение CPU/RAM production не выполнено, прежние рекомендации по скриншотам не были измерениями прода и не доказывали исправление Safari. Локальное `/dev/shm` PostgreSQL 1 ГиБ исправило конкретный отказ нагрузки, а не браузерный FPS.
- Завершение зависшего локального сервера убирает внешнюю нагрузку; это не оптимизация приложения и не доказательство причины всех лагов. Перед сравнением исключить конкурирующие процессы, а старые серии не объявлять недостоверными без проверки их условий.

Источники отрицательных опытов: [scroll/resize](journal-scroll-resize-investigation-2026-10-22.md), [layout/paint](journal-layout-cost-investigation-2026-10-22.md). Полное копирование 200000 × 111, многопользовательская нагрузка всего приложения и 360–600 тысяч документов не подтверждены узкими сценариями журнала.

## 8. Как принимать будущий перенос

- Одни данные/ресурсы, production-сборки, обычный CPU, одинаковые viewport/DPR/темы/колонки; Chrome и установленный Safari отдельно от WebKit. При блокировке экрана разрешён fallback WebKit, но не подмена названия результата. Не менять ресурсы/версию AG Grid внутри сравнения и не запускать параллельные нагрузки.
- Холодный/прогретый сценарии, прямой/обратный порядок, достаточные повторы. RAF — диагностический интервал, не физический FPS; время ввода до DOM, RPC и физический жест не смешивать. Видео/CPU-профиль снимать отдельно от чистого замера.
- Матрица: медленная/быстрая вертикаль и горизонталь, диагональ, 0/1/3 уровня групп, много коротких групп, 111 полей, узкое окно, закрепления/темы/плотности/wrap, мышь/клавиатура/трекпад, reduced motion, повторные раскрытия и возвращения.
- Помимо времени: DOM, память после одинаковых циклов, таймеры/listeners, layout/style/paint, RPC/SQL/размер ответов, доступ/ревизия/отмена, focus/reconnect, отсутствие N+1 и лишнего dispatcher rebuild. Для растущих путей — изолированные 200000 стыков либо обоснованная эквивалентная проверка сложности; документные кардинальности независимы.
- Опорные тесты: `e2e/tests/journal-server-grid.spec.ts`, `journal-resource-budget.spec.ts`, `journal-server-api.spec.ts`, `journal-copy-ranges.spec.ts`, `journal-performance.spec.ts`, `journal-filter-cache-performance.spec.ts`; предметные E2E каждого нового потребителя. Бизнес-ожидания брать из решений пользователя, не из совпадения кода и теста.
- Не обрезать данные/историю и не ослаблять проверки ради метрик. Если выигрыш не выше шума или один браузер воспроизводимо хуже — не включать эксперимент. Реальные ограничения и пропуски перечислять отдельно.

Подробные результаты держать **вне Git**, сохранять нужные воспроизводимые тесты и компактный отчёт. Архив/снимки проверенного кода: [указатель](measurements/README.md). Актуальные ограничения, завершённые и прочие отложенные темы — в [передаче чата](chat-handoff-2026-10-22-ag-grid-transfer.md).
