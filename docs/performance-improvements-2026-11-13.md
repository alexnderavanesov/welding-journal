# Ускорения после аудита — 13.11.2026

**Выполнено локально:** четыре выбранных направления ускорений реализованы, измерены до/после и проверены в Chrome и WebKit. Пользователь объединил их в одну задачу и поручил самостоятельно выбирать технические решения. Остальные идеи автоматически не возобновляются.

Для устранения задержки первого создания системного документа при будущем выпуске нужен штатный этап подготовки базы до возобновления записи. Право production-роли на `ANALYZE` остаётся непроверенным. Схема БД не менялась; миграции не нужны. Production, коммит и push в эту задачу не входят.

Выполненный объём:

- одна одновременно формируемая большая Excel-выгрузка на систему; небольшие выгрузки остаются доступны; полный файл, свежие данные и выбранные фильтры/порядок/столбцы сохраняются;
- ускорение группировок ЛНК/ПСТО и статистики;
- уменьшение стоимости чтения реестров документов с сохранением проверки актуальности всего выбранного диапазона;
- подготовка индекса системных документов до пользовательского сохранения, с сохранением истории и атомарности.

Если другая большая выгрузка уже формируется, показано понятное сообщение; повтор запускает пользователь. Автоматической очереди нет. Слот освобождается после формирования файла, при отмене и ошибке; передача готового файла не занимает слот. Ограничение общее для пользователей, вкладок и процессов приложения, работающих с одной базой.

Исходная версия: main, `7ac71600e5d26d8b6afbcc88afe124ba91abf86b` плюс существующие незакоммиченные исправления аудита и бизнес-правил. Сборка до новых ускорений сохранена в `outputs/performance-improvements-2026-11-13/baseline-output`. Сравнения выполняются только на отдельной локальной тестовой базе, Chrome — основной браузер, WebKit — затронутые сценарии совместимости.

Коммит, push, выпуск и любые production-действия не поручены. Рабочие данные и прежние правки сохраняются. Печать и её лимиты не меняются. Остальные кандидаты: [список задач для рассмотрения](tasks-to-consider.md).

Результаты и ограничения новой версии приведены ниже; предыдущие числа из [системного аудита](systemic-audit-2026-11-13.md) не подменяют эти замеры.

## Что изменено

- Общий слот Excel — транзакционная advisory-блокировка PostgreSQL в той же транзакции чтения, без дополнительного соединения и очереди. Порог: обрабатывается больше 10000 исходных/результирующих строк или 1000000 ячеек; небольшой итоговый файл тоже может потребовать большого исходного отбора. Повторный большой запрос получает HTTP 429 и понятное сообщение; ZIP завершается до освобождения слота. [Механизм блокировки PostgreSQL](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS).
- Статистика использует принадлежащие расчёту строки без материализации десятков ненужных виртуальных ячеек и нескольких полных копий. Одинаковая сводка ЛНК/ПСТО получает общий существующий кэш с прежними проверками версии, параметров и объединением одновременных расчётов. Группировки также обходятся без лишних копий; для уже нормализованных значений контроля убрана повторная обработка регистра, прежний путь для нестандартного текста сохранён.
- Версия обычного реестра по-прежнему покрывает все документы и связанные отображаемые факты; из её вычисления исключены только повторные форматированные представления тех же значений и повторение имён JSON-полей. Постраничная версия, устаревающий кэш карточек и пропуск проверки актуальности не вводятся.
- Существующая подготовка выпуска теперь заранее готовит все четыре системных индекса, в общей атомарной транзакции; повторная подготовка использует их версии. Тяжёлая работа выполняется до первого создания системного документа пользователем. Рабочий резервный путь ленивой инициализации сохранён. Подготовка production требует отдельного прямого разрешения и паузы записи.

Схема БД не менялась. Исходные результаты и сравнения находятся в `outputs/performance-improvements-2026-11-13/`. Руководство пользователя обновлено.

## Одновременные выгрузки

Пять Chrome-клиентов; приложение ограничено 4 CPU / 4 ГиБ без swap, пул — 5 соединений, временные файлы — на локальном диске. PostgreSQL и браузер вне лимита приложения. Сравнение выполнено без параллельных сборок/тестов на одном наборе: 200000 строк × 107 столбцов, файл около 80 МБ. Исходный режим — три формирующихся файла; новый — один файл и два отказа с возможностью ручного повтора. Это уменьшение одновременной нагрузки, а не ускорение суммарной выдачи трёх файлов.

| Наблюдение | До | После |
| --- | ---: | ---: |
| Готовность большого файла | 262,9 с для каждого из трёх | 93,4 с для одного; ещё два получают сообщение примерно за 3,9 с |
| Три параллельные операции редактирования | 6,9–8,4 с | 4,8–5,9 с |
| Небольшой файл во время большой выгрузки | — | 0,60 с |
| Очистка после отмены | 0,42 с | 0,43 с, общий слот освобождён |
| Полный повтор после отмены | 87,9 с | 88,8 с |

Проверены все 200000 уникальных стыков, полный набор/порядок 107 столбцов и строк, отсутствие изменений исходных фактов, очистка временных файлов, освобождение реально занятой блокировки и повторное скачивание. OOM и аварий процесса нет. **Стабильного ускорения поиска и снижения пиковой памяти не получено:** приложение около 2,1 ГиБ в обоих случаях. Одна большая выгрузка всё ещё использует общие ресурсы сайта.

При намеренной отмене закрытого HTTP-запроса серверный фреймворк пишет `AbortError` с внутренним статусом 500; это воспроизводится и до изменения. Сопоставлены момент отмены, очистка, состояние процесса и успешный полный повтор; падения приложения не выявлено. Диагностический шум сохранён в логах, глобальная обработка ошибок в этой задаче не менялась.

Основные доказательства: `export-before-clean-results/**/concurrent-exports.json`, `export-after-v2-results/**/concurrent-exports.json`. Для таблицы использован чистый повтор без параллельных проверок; ранние диагностические запуски также сохранены.

## Подготовка индекса перед работой пользователей

Парное сравнение на новых изолированных базах: 200000 фоновых стыков в смешанных цепочках R/W/Y, 400000 заключений, один отдельный стык для реального сохранения результата ЛНК через интерфейс. Приложение и подготовка без отдельного лимита 4 CPU / 4 ГиБ; настройки локального PostgreSQL одинаковы.

- До: первое сохранение результата с созданием заключения — **65,9 с**.
- После штатной подготовки выпуска: такое же сохранение — **0,84 с**.
- Сама предварительная подготовка — **21,3 с**, повторная — **7 мс**.

Сохранены все фоновые фактические данные и связи цепочек. Повторная подготовка сохраняет полные контрольные суммы документов и их состава, включая идентичность записей; маленький сценарий с искусственной ошибкой отдельно проверяет атомарный откат. После сохранения — 400002 документа и столько же связей.

Эффект относится к созданию нового документа с проверкой названия, а не к каждому обычному изменению карточки. Успешные парные результаты: `index-before-v4-results/**/release-index-preparation.json`, `index-after-results/**/release-index-preparation.json`; исправленные предположения раннего измерителя описаны в `index-harness-diagnostics.json`.

Право production-роли на `ANALYZE`, отмеченное в исходном аудите, по-прежнему не проверялось; production-подключений и подготовки в этой задаче не было.
