# Передача контекста в новую задачу Codex

Обновлено: 12.08.2026.

## Как пользоваться этим файлом

Этот файл передает только рабочее состояние проекта. Он не заменяет код, тесты и пользовательское руководство и не должен превращаться в копию старой переписки.

Перед любой новой работой:

1. Прочитать `AGENTS.md`.
2. Выполнить `git status --short`, `git diff --stat` и `git log -5 --oneline`.
3. Не сбрасывать и не перезаписывать незнакомые изменения: текущее рабочее дерево содержит большую проверенную серию еще не закоммиченных изменений.
4. Для продуктовых правил сверяться с `src/components/user-guide-page.tsx`, профильными тестами и существующей реализацией.
5. После изменений запускать проверки в масштабе риска; перед коммитом использовать `pnpm verify`.

## Что находится в незакоммиченной серии

Серия объединяет связанные изменения по следующим контурам:

- серверный и фоновый индекс задач диспетчера, виртуальное поле кодов ДЗ, принятые исключения и связанные настройки;
- проверки ЗВ/ДЗ, итоговая валидация импорта после объединения с записью БД и вывод всех одновременно найденных ошибок;
- цепочки стыков, системные индексы имен и строгая проверка формы/сервера;
- документы и шаблоны, системные документы, нумерация и хранилище шаблонов;
- статистика, серверные агрегаты, фильтры и производительность больших таблиц;
- реестр клейм, НАКС/ДЛС и проверки на стороне сервера;
- импорт, массовое заполнение и замена данных;
- обновления зависимостей, Netlify-функции и конфигурация.

Сгенерирована миграция `drizzle/0023_glamorous_payback.sql` для фонового индекса диспетчера. Источником схемы остается `src/db/schema.ts`; SQL миграций вручную не редактировать.

## Последняя завершенная функция

Для режима Excel `Замена данных` добавлена защита от перезаписи более свежих изменений другого пользователя:

- свежий шаблон содержит скрытую техническую версию каждой строки;
- обычный импорт и массовое заполнение не изменены;
- неизмененные строки старого файла игнорируются;
- измененная или удаляемая строка со старой версией блокируется в предпросмотре;
- сервер повторно проверяет версии внутри транзакции после блокировки строк;
- при конфликте вся операция замены отменяется целиком;
- пользователю предлагается скачать свежий шаблон.

Основные файлы этой функции:

- `src/lib/weld-row-version.ts`;
- `src/lib/report-import-template.ts`;
- `src/lib/report-import-preview.ts`;
- `src/lib/use-report-import-mutations.ts`;
- `src/server/welds.ts`;
- соответствующие тесты и `src/components/user-guide-page.tsx`.

Для этой функции миграция БД не требуется: версия читается из PostgreSQL `xmin` и не хранится отдельной колонкой.

## Неподвижные правила проекта

- Документы являются только способом вывода данных. Они не меняют сварочную логику, проверки, задачи диспетчера, заявки или результаты.
- Уникальная бизнес-связка стыка: проект + шифр + линия + стык. Дубликаты не запрещаются жестким ограничением БД: их показывает диспетчер и цепочка.
- Импорт, массовое заполнение и замена проверяют итоговую запись после наложения данных Excel на сохраненный стык.
- Если в строке есть несколько ошибок, предпросмотр должен показать и подсветить их все, а не останавливаться на первой.
- Любое изменение правила диспетчера, способное затронуть существующие стыки, требует увеличения `DISPATCHER_TASK_CALCULATION_VERSION`.
- Каждая новая пара ЗВ/ДЗ требует тестов формы/сервера, кода задачи, сохраненного индекса и виртуального поля `dispatcherTasks`.
- Любое пользовательское изменение функций, правил, импорта, документов, диспетчера или настроек сопровождается обновлением `src/components/user-guide-page.tsx`.

Подробные правила клейм, НАКС/ДЛС, архивов, документов, РК, ЛНК/ПСТО, ЗВ/ДЗ и конструктора уже описаны в пользовательском руководстве и закреплены тестами. Не восстанавливать их по памяти из старой переписки.

## База данных и production

- Локальная разработка использует локальный PostgreSQL.
- Для схемы сначала меняется `src/db/schema.ts`, затем запускается `pnpm db:generate`.
- Локальные миграции: `pnpm db:migrate`.
- Удаленную БД сначала проверять через `DATABASE_URL_REMOTE_FOR_MIGRATIONS` и мигрировать только командой `pnpm db:remote-migration`.
- Не использовать обычный `DATABASE_URL` для удаленных миграций и не запускать `drizzle-kit migrate` напрямую против production.
- Состояние применения миграции `0023` к удаленной БД нельзя предполагать по этому файлу: его нужно проверить перед следующим запросом пользователя на миграцию или деплой.
