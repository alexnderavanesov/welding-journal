## Авторизация: согласовано, но не реализовано

Прочитать **весь** [план](authentication-and-access-plan-2026-10-29.md); следующие пункты — ориентир, не замена требований и технических оговорок.

- **Better Auth**, вход по почте/паролю, только приглашение администратором. Около 25 пользователей — начальный ориентир без жёсткого лимита. Общие пароли заменяются личными правами. Должность сама по себе права не выдаёт.
- Защищённый владелец: **Аванесов Александр, Директор, a.avanesov@yums.ru**. В приложении его нельзя удалить, заблокировать или лишить прав. Только владелец управляет администраторами; администраторы — обычными пользователями. Владельца готовят управляемой одноразовой процедурой с защитой устойчивого ID, не назначают первому посетителю.
- Пароль минимум **6 символов**; приглашение **48 часов**, восстановление **1 час**, сеанс **24 часа с продлением при работе**. Восстановление инициирует администратор, пользователь сам задаёт пароль по одноразовой ссылке; восстановление администраторов — владельцем. Публичное самостоятельное «забыли пароль» пока не вводится. Аварийное восстановление владельца требует уполномоченного доступа к серверу/БД, одного GitHub недостаточно.
- Под настройками — личный раздел с ФИО, должностью, неизменяемой почтой, сменой пароля и выходом. Администратору — панель пользователей, приглашений, прав и восстановления. Почта видна самому пользователю и администратору, редактирование закрыто и в API. Удаляется аккаунт, а не переносится в архив; сеансы/токены отзываются, исторические ФИО и рабочие данные сохраняются. Повторное приглашение той же почты создаёт новую личность.
- Гибкие права на разделы и действия, включая ЛНК, ПСТО/ТВМТ, документы, программу линий, справочники и статистику. Настройки разделены: шаблоны, ДЗ/проверки, нумерация и другие группы. Общий журнал действий и история стыка — отдельные разрешения. Инженеры по умолчанию читают связанные данные, меняют свою область; администратор может изменить набор. Сервер проверяет каждый защищённый путь, файлы, RPC, кэши, запрещённые поля и права плагинов; UI-галочек недостаточно.
- История **всех рабочих полей** стыка, создание/удаление, значимые настройки и управление доступом. Предлагается общая операция с автором/снимком ФИО и пакетные подробности только изменившихся значений, записанные в той же транзакции. Общий журнал и история стыка читают один источник постранично; обязательны фильтры даты/времени, автора и типа. Технические кэши, просмотры и пароли/токены не журналировать. Старым изменениям не выдумывать авторов; автоматическую очистку истории не вводить. Точную схему, объём и стоимость подтвердить при разработке.
- Служебные даты в БД остаются. В плане выбрано скрыть «Внесён/Создан» и «Обновлён» в стандартном представлении, сохранив выбор колонок и прежние пользовательские раскладки. Это ещё не реализовано.
- Отправитель **system@yums.ru**, Яндекс Почта; пользователь уже подтвердил первичную готовность ящика. Отправитель заменяем через серверную конфигурацию. SMTP приложения и доставка ещё не настроены/не проверены. Основной пароль не нужен: отдельный пароль приложения хранить как серверный секрет, не просить в обычном чате. Локальная разработка — изолированный приёмник писем без реальной отправки. Настройки почты/DNS, production bootstrap и первое реальное письмо — только в отдельно разрешённом выпуске.
- Сейчас один рабочий набор данных. Будущая экосистема персонала/материалов/финансов учитывается в границах модулей, но рабочие пространства, отдельные новые БД, SSO/MFA и конструктор прав для каждого из 111 столбцов не добавляются автоматически. MCP документации `better-auth` и шесть официальных skills установлены; штатный MCP проверен после перезапуска 29.10. В текущем каталоге инструменты доступны. **Better Auth отсутствует в package.json/lockfile**, что повторно проверено при передаче. Не устанавливать повторно инструменты. ## Ограничения и первый ответ нового чата

- **До финального согласования — только чтение и обсуждение.** Не начинать код, прототип, зависимости, аудит/тесты, миграции, commit/push/deploy. Старые разрешения на выпуск уже исполнены и не переносятся на авторизацию.
- Сохранять checkout/main, рабочие данные, резервные копии и незакоммиченные документы; без worktree, переключения ветки, reset/stash, остановки серверов или одновременных запусков с общей БД из двух чатов. Старый чат не архивировать и сообщения ему не отправлять.
- **Без субагентов по умолчанию**; делегирование только после отдельного подтверждения конкретной пользы. В полном аудите глубина важнее экономии, но это не разрешает агентов. Модель/уровень выбирает пользователь, автоматически не менять.
- Production — реальные пользователи: отдельное прямое разрешение для конкретного изменения данных, схемы, конфигурации, серверов, контейнеров, почты и выпуска. Read-only доступ не разрешает тесты, нагрузку или скрытые записи при чтении. **Не восстанавливать прод старым дампом.**
- После отдельно разрешённой реализации сохраняется постоянное разрешение на **проверенные локальные миграции** на main, включая рабочую БД, с сохранением данных: схема → `pnpm db:generate` → просмотр → `pnpm db:migrate`. SQL не писать вручную. Это не поручение мигрировать сейчас. Remote — только отдельное разрешение и штатный `pnpm db:remote-migration`.
- Fixtures/нагрузка/автотесты только в отдельной проверенной пустой локальной БД и отдельном хранилище; рабочую БД не очищать/не подменять. При изменении поведения обновлять встроенную инструкцию; сохранять бизнес-правила, версии, атомарность и историю.

Первое действие: прочитать AGENTS.md, эту передачу, **полный план авторизации**, актуальную верхнюю часть отчёта выпуска и полный отложенный план оптимизации. Остальные перечисленные планы сохранять как отдельные темы и читать полностью перед их обсуждением. Проверить актуальный Git без изменений. Первый ответ — коротко подтвердить ограничения и перечислить, что требует финального согласования/технической проверки, **затем ждать пользователя**. Не начинать новый аудит или реализацию под видом подготовки.
