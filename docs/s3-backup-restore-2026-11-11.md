# Репетиция резервного копирования и восстановления S3 — 11.11.2026

**Результат: восстановление БД вместе с PDF подтверждено на синтетических данных.** Production и рабочая БД не использовались; коммит/push не выполнялись. Код приложения и схема БД не менялись. Это проверка способа восстановления, а не настройка регулярного production-бэкапа.

**Решение пользователя, 11.11.2026:** проверку существующего production-резервирования остановить и двигаться дальше, приняв подтверждение сисадмина о его настройке. По скриншотам Selectel подтверждены настройки БД: полная копия еженедельно, инкрементальная ежедневно, хранение 7 дней. В приватном `welding-journal-production-backups` показаны 97 объектов / 95,88 МБ. Свежесть, состав и исправность конкретных копий не проверены; дата в форме точки восстановления не принята за время успешного бэкапа. Production не менялся, резервирование/восстановление не запускались. Эту проверку без нового поручения не продолжать. Включение будущего production-бакета PDF в резервирование остаётся частью подготовки его подключения, а не подтверждённой возможностью существующих резервов.

Созданы две новые пустые локальные БД: `welding_tracker_s3_backup_20261111` и `welding_tracker_s3_restore_20261111`. Обвязка проверяет отсутствие существующих БД и принадлежность созданных по OID. Источник получил существующие миграции на `main`; целевая БД восстановлена через `pg_restore --single-transaction --exit-on-error`. PostgreSQL/pg_dump — 18.4. Только приватный тестовый бакет `welding-journal-schemes-test`.

В копии — дамп всей тестовой БД и **три разных PDF: основной и две архивные редакции**, с двумя точками, обозначением, многострочным примечанием и размером у каждой редакции. Дамп и перечень PDF читаются из одного экспортированного снимка PostgreSQL; приложение и другие писатели источника остановлены. PDF скачиваются по точным ключам редакций, включая архивы, с проверкой размера и SHA-256 из метаданных загрузки. Конечный `manifest.json` появляется только после получения полного комплекта. Копия хранится локально, отдельно от S3; ключи доступа S3 туда не включаются. Права каталогов 0700, дампа 0600; поиск фактических S3-ключей в 485 файлах обвязки/артефактов совпадений не дал.

После создания копии исходная одноразовая БД удалена, все три текущих PDF удалены из S3 с подтверждением отсутствия. Восстановление использовало **только дамп и скачанные файлы**, без исходной БД и чтения исторических S3-версий. На восстановленной БД полностью совпали содержимое всех 45 таблиц, значения последовательностей и определения колонок. Все PDF побайтно соответствуют контрольным суммам; ключи, связи, основной/архивный статус и вся разметка сохранены.

Дополнительно проверены:

- Отсутствующий PDF, повреждение PDF без изменения длины и повреждённый дамп обнаруживаются проверкой копии. Незавершённая выгрузка при отсутствии исходного S3-файла не получает конечный манифест.
- Восстановление только БД не считается завершённым, пока нет PDF. Манифест, из которого исключены архивы, отвергается по сравнению с восстановленными редакциями.
- Другой объект под восстанавливаемым ключом не перезаписывается; весь проход останавливается до загрузки остальных файлов.
- После восстановления одного PDF повтор добавляет два оставшихся; следующий повтор не выполняет новых записей. Отдельный контрольный объект вне инвентаря остаётся неизменным. Бакет целиком не перечисляется и не очищается.
- Восстановленное приложение запущено в **Linux arm64 / Node 22.23.2**. Chrome и WebKit открыли основной PDF и оба архива, проверили точки/размеры/примечания, полное чтение и Range. Чтение без входа возвращает 401. Новый размер сохраняется, остаётся после обновления страницы и затем возвращается к исходному значению.

Первый браузерный прогон выявил гонку в новой проверке: отключённая кнопка трактовалась как завершённое сохранение, хотя она отключена и во время запроса. Trace показал правильный payload и ответ 200 после преждевременного чтения БД. Тест теперь ждёт ответ сохранения; ожидаемое значение не менялось. Повтор всей репетиции и оба браузера прошли. TypeScript и `git diff --check` прошли; серверный журнал успешного прогона без ошибок. Предупреждения фикстуры Better Auth о запросе без IP и Playwright о цветном выводе не относятся к восстановлению.

Обе БД, контейнер, временные каталоги и четыре собственных текущих S3-объекта каждого прогона удалены; отсутствие объектов подтверждено HEAD. Исторические версии остаются. Рабочий сайт 3000 продолжает работать. Проверенные копии и диагностика сохранены вне Git с закрытыми правами: успешный прогон — `outputs/s3-backup-2026-11-11-sVZqUh/`, первый прогон — `outputs/s3-backup-2026-11-11-kDe5kT/`. Комплект — `backup/`, результаты — `report.json`, `cleanup.json`, `container.log`, снимки Chrome/WebKit. Команда повторения: `node --import tsx e2e/run-s3-backup.ts --allow-test-writes`.

**Границы:** набор небольшой; длительность восстановления и объём резервов production не измерялись. Автоматическое расписание, срок хранения, независимое удалённое хранилище резервов и восстановление серверных секретов не настраивались. В тесте сервер использовал сохранённую в памяти тестовую конфигурацию. Для полного резерва приложения отдельно нужны исходные Excel-шаблоны из постоянного volume и защищённая копия необходимых настроек/секретов; их восстановление не входит в эту проверку БД + S3 PDF. Проверка комплектности выполняется обвязкой репетиции, не является новой автоматической блокировкой приложения.

Старые PDF были тестовыми: перенос в production по решению пользователя **не требуется**.
