Доступность полей определяется существующим профилем ПСТО. Новые способы записи через вставку или протягивание ячеек не добавляются; разрешённые правки выполняются прежними формами.

## Итоги групп и вывод отчёта

Общие итоги переносим из журнала:

- «Линия» — разные линии с учётом проекта и шифра; при группировке по линии показывается её обозначение. «Стык» — физические соединения. `S1 → S1R1 → S1R2` даёт одно соединение; после замены катушкой старое исключается, две стороны считаются отдельно.
- WDI — сумма по физическим корням без повторов ремонта; дата сварки — диапазон дат записей группы; проект и шифр — общее значение при полном совпадении.
- Общий итог стыка сохраняет правила журнала: ошибка важнее всего, включая историю; затем ранний незавершённый этап и отдельный счётчик брака. Завершённый ремонт не ухудшает итог историческим браком; неполная цепь не получает ложный «годен».
- Фильтры выбирают записи, а не агрегаты групп. В ПСТО часть цепи может отсутствовать уже из-за состава отчёта, даже без пользовательского фильтра. Сохраняем понятное обозначение неполноты и пакетные сведения о физических корнях; не подгружаем всю линию ради итога.

**Согласованный первый этап:** общие итоги выше и отдельные итоги «Результат ПСТО»/«Результат ТВМТ» по тем же физическим соединениям. Ошибки соответствующего этапа учитываются во всей загруженной истории; затем показывается раннее ожидание и отдельно оставшийся текущий брак. Учитывается текущий цикл, как в строке ПСТО; завершённый повтор не остаётся негодным из-за предыдущего цикла. Отмена не скрывает фактическую негодную ТВМТ. Неполная цепь обозначается явно; смешанные завершённые/отменённые/ненужные этапы не получают ложное общее завершение. Подсказка раскрывает число физических соединений по состояниям. Поля циклов, документов и дат этапов остаются без новых агрегатов.

**Согласовано по «Показать → Текущая версия»:** перенести поведение журнала — видимые столбцы ПСТО в экранном порядке, все строки текущего серверного отбора, без экранной группировки и служебных столбцов. Это явное изменение нынешнего фиксированного набора полей текущего отчёта ПСТО. Скрытие всех полей даёт понятное объяснение вместо пустой выгрузки. «Ожидание заявки» и «Результаты ПСТО» сохраняют собственные состав и правила. Предпросмотр, полный Excel, предел формирования и печать до 1000 строк остаются действующими. Копирование диапазона сохраняется как отдельное действие.

## Что сохраняется в работе ПСТО

1. **Состав и смысл строк.** Назначенные, официально отменённые и сохранившие историю записи остаются доступны по текущим правилам. Отображается текущий основной или повторный цикл; подписи, фильтры, сортировка, копирование и вывод должны согласованно использовать его значения. История соседнего стыка не подменяет собственную; ожидание не считается доказательством начатого процесса.
2. **Все рабочие входы.** Верхние меню ПСТО/ТВМТ, «Действия ПСТО» в строке, ПКМ одной/нескольких записей, история циклов, «Следующее действие», программа ПСТО, картина стыка, переходы в журнал/ЛНК и к документам. Сохраняются причины недоступности, ожидание загрузки, ошибка и повтор. Ссылки заявок, диаграмм и заключений открывают точный документ в предпросмотре; редактирование остаётся отдельным действием.
3. **Циклы и документы.** Основной и повторные циклы, отдельные заявки ПСТО/ТВМТ, точный цикл каждой позиции документа, негодная ТВМТ и следующий повтор, обязательные реквизиты, хронология, официальность, зависимости и подтверждения исправления/удаления. Один документ может содержать разные циклы разных стыков; это не меняет идентичность позиции.
4. **НК до ТО и специалисты.** Четыре согласованных сценария назначения/возобновления, отмены и перемещения на линии с/без ПСТО сохраняют исходный KEEP, выбор по стыкам, перенос полного допустимого комплекта и атомарность. Снимки ФИО/удостоверений сохраняются; конфликтующее объединение требует прежнего подтверждения очистки обеих ролей только конфликтующего документа. Основа — [план специалистов](specialists-plan-2026-10-12.md), с приоритетом четырёх сценариев над ранними описаниями двух.
5. **Защита данных.** Системные назначения, заявки, результаты, даты и документы не становятся свободно редактируемыми ячейками. Права, версии, отказ устаревшему окну, отмена, повтор и атомарный откат сохраняются. Логика диспетчера и правила расчёта этапов не меняются ради новой таблицы.

## Технический способ переноса

Выделить из текущего журнала небольшую общую основу таблицы стыков с двумя профильными подключениями — журнал и ПСТО. Переиспользовать уже работающие фильтр, toolbar, ячейки, группы, фокус, прокрутку и статистику диапазонов. Параметризовать реальные различия; не копировать весь компонент и не создавать универсальную систему для всех таблиц приложения.

| Участок | Необходимая адаптация |
| --- | --- |
| `welding-journal-grid*`, `welding-journal-grid-state.ts` | Профиль отчёта, независимый ключ хранения, заголовки/доступные имена, объединение раздела ПСТО и рендерер его `rowActions`. Существующие `getPstoDisplayValue`, проверки редактирования и обработчики переиспользуются. Ключ журнала и его сохранённые виды сохраняются. |
| `welding-journal-grid-filter.tsx` | Запрос значений и ключ кэша получают `heatTreatment` для ПСТО вместо жёсткого `weldingJournal`. Сохраняются скрытые фильтры переходов, поиск, отмена и серверная область отбора. |
| `report-main-content.tsx`, `home-page-view.tsx`, `report-workspace.tsx`, `report-task-panels.tsx` | Подключение нового профиля, lazy loading, геометрия/панели по образцу журнала. Переключение отчётов не переносит старые настройки, выбор или поздний ответ в другой отчёт. |
| `weld-read.ts`, `journal-group-context.ts` | Для обеих веток чтения ПСТО добавить такой же пакетный контекст корней по ID текущей страницы. Сейчас он подключён только к журналу. Сохранить порционность и существующую семантику чтения ПСТО. |
| `use-report-output-actions.ts`, экспортные поля | Для согласованной текущей версии читать порядок/видимость столбцов активного ПСТО. Не использовать оставшуюся ссылку на колонки журнала после перехода. |
| `user-guide-page.tsx` и `user-guide-content/work-sections.ts` | Описать новый вид ПСТО, настройку, клавиатуру, группы и физический счётчик, область выбора и согласованный вывод. |

Серверная пагинация, фильтрация и сортировка сохраняются. AG Grid работает с загруженными строками; группировка остаётся в пределах этой части выборки. Группировка, resize, выделение и копирование не должны вызывать запросы на строку/группу. Контекст корней добавляется пакетно, без выкачивания всего журнала. Схема, зависимости и миграции для переноса не предполагаются. Вопрос совместимой лицензии AG Grid перед выпуском остаётся отдельным существующим ограничением.

## Порядок реализации

1. **Зафиксировать критерии.** Сопоставить поля/действия текущего ПСТО с базой журнала и двумя предложениями об агрегатах/выводе выше. Снять сопоставимые исходные показатели запросов, DOM и отклика затронутых сценариев на изолированных данных.
2. **Выделить общую основу.** Параметризовать журнал, сохранив его поведение и настройки; выполнить регрессии эталонного журнала до подключения ПСТО.
3. **Подключить ПСТО.** Перенести оболочку таблицы, профильные столбцы, действия и текущий цикл; затем фильтры, настройки, группировки, пакетный контекст и согласованный вывод. Существующие бизнес-окна остаются источником рабочих операций.
4. **Провести приёмку.** Проверить таблицу и сквозные процессы ПСТО, регрессию журнала и переходов в ЛНК, запросы и масштаб. Исправить подтверждённые регрессии; удалить только код, ставший ненужным. Общая прежняя таблица остаётся необходимой ЛНК.
5. **Завершить документацию.** Обновить руководство, записать фактический объём проверок и ограничения. Передать результат для локального просмотра без автоматического коммита или выпуска.

## Фактическая реализация и проверка

Основная таблица ПСТО подключена к `WeldReportGrid`, выделенному из текущего журнала. ### Прежнее ограничение и последующее поручение

**Актуализация 19.10:** после приведённой ниже оценки пользователь поручил исправить ограничение и выполнить полную предкоммитную проверку без коммита. Адресное чтение реализовано; результаты последующей проверки фиксируются отдельно в `precommit-audit-2026-10-19-psto-dispatcher.md`. Ниже сохранено исходное описание риска, а не действующий статус согласования.

При более чем 5000 задачах диспетчера картина стыка может не показать действие для цепочки за пределами загруженного snapshot. В трассе сценария исправления имён расчёт был актуален, но из 16970 задач переданы первые 5000; задачи S991 отсутствовали, и команда переименования не появилась. Связанные алгоритм, окно и граница snapshot совпадают с исходным снимком до переноса ПСТО; проблему проявили оставшиеся нагрузочные fixtures. Их очистка устраняет влияние на обычные тесты, но **не исправляет этот продуктовый предел**.

Это отдельная незавершённая работа: загружать задачи выбранной линии/цепочки с проверкой актуальной ревизии, сохраняя ограниченный общий snapshot, и проверить действие за пределом первых 5000 задач. Участки: `src/server/dispatcher-task-index.ts`, `src/lib/use-home-page-controller.tsx` (`adviceRepeatedJointTasks`), `src/components/joint-chain-dialog.tsx`. Перенос ПСТО не меняет эту архитектуру и не объявляет такой сценарий успешно проверенным.

**Уточнение риска 19.10, по запросу пользователя; исправление ожидает решения.** Лимит относится к первым 5000 карточкам СП/ДЗ по стыкам во всей базе, а не к 5000 стыкам или одной линии. У стыка может быть несколько задач; напоминания о сроках клейм передаются отдельно. Порядок первоначальной порции технический — проект/подтитул/линия, не приоритет проблемы. Сам серверный расчёт, полный индекс кодов и сохранённые страницы задач этим пределом не обрезаются.

| Экран | Что может быть упущено |
| --- | --- |
| Картина стыка из журнала, ЛНК и ПСТО | Конкретная карточка и кнопка диспетчерского действия. В прежней браузерной трассе подтверждено отсутствие «Переименовать S991R1 → S991W1 (+1 далее)» при 16970 задачах. |
| «Требует действия» | Детали/кнопки отсутствующих задач. При наличии свежих серверных кодов СП/ДЗ они остаются с подписью «Описание действий обновляется»; нулевой счётчик не является обязательным исходом. |
| Картина линии | Неполные списки/счётчики; если ни одна задача линии не загружена, возможно неверное «На линии нет активных задач». |
| «Следующее действие» в отчётах и «Что дальше» | Подсказка из задачи может уступить общей подсказке по состоянию стыка. Это не означает исчезновение всех обычных действий. |

Последние три эффекта установлены по коду, отдельный браузерный сценарий для каждого сейчас не выполнялся. Факты, результаты контроля, документы и состав цепочки загружаются независимо; серверные проверки сохранения сохраняются. Колонка СП/ДЗ и серверные фильтры используют полный индекс. Поиск в основном диспетчере обращается к полным сохранённым страницам и позволяет найти отсутствующую карточку; прямое действие из найденной карточки доступно. Однако переход из неё в картину передаёт строку и ключ, не саму задачу, поэтому подробности там опять могут отсутствовать. Ручная дозагрузка диспетчера помогает только для догруженных карточек текущей ревизии; перезагрузка страницы не гарантирует исправления.

Риск — пропуск необходимой работы оператором и ложное впечатление, что проблем нет; потери сохранённых данных из этого ограничения не установлено. Текущее число задач production не проверялось. Рекомендация для обсуждения: исправить до эксплуатации с большой очередью, сохранив ограниченную общую загрузку и добавив адресную загрузку линии/цепочки и пакетный контекст задач видимых строк. Проверить задачи за пределом 5000 во всех трёх отчётах, переход из поиска диспетчера, смену ревизии и ограниченное число RPC. Простое увеличение лимита только отодвинет границу. Это предложение, не согласованный запуск реализации.
