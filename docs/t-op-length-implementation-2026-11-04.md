# Т-04: единая длина опоры и её ремонтов

**Уточнение 05.11.2026:** это исторический отчёт проверки длины на первоначальном этапе 04.11. Последующее решение запрещает две группы материалов и несколько способов сварки на Т; упоминание их прежней положительной проверки ниже не является действующим правилом. Правила единой L сохранены. Актуальные требования — в [итоговом плане](t-op-implementation-plan-2026-11-03.md), последующие результаты — в [журнале реализации](t-op-implementation-progress-2026-11-04.md). Исторические числа прогонов не изменены.

Локальная реализация и проверка участка Т-04 завершены. Финальные профили: Chrome **33/33**, WebKit **60/60**; все 11 сценариев `t-op-weld-core.spec.ts` прошли в обоих браузерах, включая перенесённый ремонт и два конкурентных переноса/L. Подтверждены создание/редактирование Т, атомарная L цепочки R1…R12, сохранение фактов/документов, устаревшие и конкурирующие изменения, R13 и запрет катушки. Синтетические проверки используют только одноразовую локальную БД. Сгенерированная миграция отдельно применена к рабочей локальной БД с сохранением 83 записей; см. [общий журнал](t-op-implementation-progress-2026-11-04.md). Прод не изменялся, коммита нет.

- L ремонта доступна только для просмотра. Форма, итоговая серверная запись и предпросмотр массового заполнения/замены запрещают отдельную правку L ремонта. Предпросмотр показывает её одновременно с независимыми ошибками строки, включая второй индекс клейма.
- Исправление L исходного ОП распространяется на все его ремонты в той же транзакции: одиночное сохранение, пакет, массовое заполнение и замена. Новое продолжение наследует полную длину. Пустая длина распространяется как пустая; десятичная часть не округляется.
- Связь определяется сохранёнными `physicalRootId`; одноимённые самостоятельные опоры не смешиваются. Для истории без сохранённой структуры используется разрешение исходного номера с теми же правилами выбора официального тёзки. После штатной перестройки официальности длина согласуется с восстановленной физической цепочкой.
- Обновление потомков меняет только L и временные отметки/версию строки. Результаты, назначения, связанные истории и документы не переписываются. Применяются блокировки линии и строк, существующая проверка версий поданных строк; изменения потомков делают их старые версии непригодными для последующих сохранений. Для замены через импорт блокировка неизменной линии перенесена перед блокировками строк.
- Дополнительные запросы не выполняются для С/У и несвязанных исправлений Т. Распространение выполняется пакетами до 1000 строк; определение исходных опор — линейный проход, без обхода всех предков для каждого R.
- L проходит форму, импорт, БД, наследование, прямое поле шаблона, Excel и копирование как десятичная строка. Сохраняется, например, `600.123456789123456789`; проверено, что параметр SQL распространения содержит все цифры. Сумма выбранных ячеек L считается точно на клиенте и в SQL, без преобразования L в `double precision`; остальные числовые поля сохраняют прежний расчёт. Общее среднее в нижней строке остаётся прежним округлённым показателем. Произвольные арифметические формулы пользовательского Excel-шаблона сохраняют обычную числовую точность Excel; прямое поле L точное.

Проверка: общий целевой пакет Т-04/06/07 — **12 файлов, 339 тестов**, лог `outputs/t-op-controls-length-2026-11-04/unit.log`. В том числе 2001 ремонт, очистка/дробная L, устойчивые идентификаторы, неофициальные/неактуальные ремонты, проверка узкого состава SQL-записи и передача ошибки транзакции. Реальный откат и межпроцессная конкуренция БД отдельно подтверждены сценариями E2E.

После перевода L в точную десятичную строку: **9 файлов, 65 тестов**; лог `outputs/t-op-controls-length-2026-11-04/precision-unit.log`. Проверены более 18 дробных знаков, различная степень десяти, сохранение строки в файле, сумма пересекающихся диапазонов без дублей, смешанный диапазон L/D1, SQL NUMERIC и отказ выдавать итог при устаревшей версии. TypeScript приложения и отдельная компиляция `e2e/tests/t-op-weld-core.spec.ts` прошли. Полный интеграционный запуск и его результаты ведёт общий отчёт.

Дополнительно проверены технические границы хранения NUMERIC: до 131072 цифр перед десятичным разделителем и до 16383 после него, согласно [документации PostgreSQL](https://www.postgresql.org/docs/current/datatype-numeric.html). Значения вне представимого диапазона получают понятную СП-13 до записи, одновременно с другими ошибками импорта; округление не используется. Целевой пакет после этой проверки: **8 файлов, 167 тестов**, `outputs/t-op-controls-length-2026-11-04/numeric-bounds-unit.log`.

Успешные E2E дополнительно охватывают UI создания/редактирования Т, объединённые ошибки и откат импорта, блокировку смены семейства, ТК и оба материала/способа единственного клейма, сохранение документов/фактов при изменении L, устаревшие одиночные и пакетные сохранения, конкурирующие изменения исходной L, R13 и запрет катушки. Перед коммитом остаётся согласованная репетиция на свежей выгрузке пользователя.

После первого Chrome-прогона независимая проверка выявила пропуск: распространение читало только текущую линию исходного ОП и не охватывало сохранённый ремонт на другой линии. Новая регрессия воспроизвела пустой список изменений до исправления (`moved-before.log`). Выборка дополнена авторитетной связью `physicalRootId` по всем линиям; независимые тёзки не включаются. Для изменения L все затронутые линии блокируются единой отсортированной группой до блокировок строк, состав и расположение повторно проверяются. При изменении снимка операция отклоняется до записи.

Дополнительные линии потомков регистрируются в явном `WeakMap` конкретной транзакции и объединяются с её штатной завершающей инвалидизацией диспетчера. Глобальная блокировка диспетчера не переносится перед работой с документами. Регрессии подтверждают один итоговый SQL, изоляцию транзакций, очистку после успеха и сохранение полного пересчёта. Пакет — **7 файлов, 140 тестов**, `moved-unit.log`; приложение и E2E компилируются. Реальный сценарий разделённой старой истории для single/batch/replace/mass, СП-03 другой линии, тёзки и конкурирующей правки ремонта прошёл в финальных Chrome и WebKit.

Оба детерминированных DB-race сценария «L и перенос B→C» прошли в финальных Chrome и WebKit 04.11: обе операции используют аутентифицированный HTTP API, порядок подтверждается через `pg_blocking_pids` за удерживаемой блокировкой строки. Один тест ставит перенос первым, второй — L. Подтверждены отклонение устаревшего снимка/версии и успешный свежий повтор без частичного изменения L, фактов, документа или соседней записи; проверены dirty scopes и сохранённый физический root. Проверка не меняет ограничения обычного переноса: используется полная локальная цепочка B с сохранённой исторической связью R2→A.

В промежуточном прогоне отдельная проверка СП-03 перенесённого ремонта обнаружила ошибку fixture: счётчик объединял отсутствие L с оставленными пустыми фактическими клеймами. Распространение L и инвалидизация уже прошли, но после заполнения L законно оставалось другое напоминание СП-03. Для изоляции проверки fixture дополнена фактическими клеймами и нулевой исходной проверкой СП-03. Ожидание исчезновения задачи не ослаблено; исправленный сценарий прошёл в финальных Chrome и WebKit.
