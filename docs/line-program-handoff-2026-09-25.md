## А. Постоянные правила и ограничения

- **Production — только просмотр без изменения состояния.** `https://welding-journal-test.yums.ru/journal` считается production, несмотря на `test` в имени. Разрешены безопасный просмотр, поиск и фильтры, когда нужны для задачи. Запрещены редактирование, создание, сохранение, удаление, тесты, нагрузка, миграции, пересчёты, обслуживание, изменения настроек, кода, схемы, документов и инфраструктуры. Сомнительный «просмотр», который может писать данные, сначала проверить по локальному коду либо уточнить.
- **Не запускать автодеплой пушем.** Старые разовые разрешения на production-миграцию/деплой из предыдущих сообщений больше не действуют. Общая просьба «пуш» не снимает нынешнюю production-границу: пользователь должен явно изменить ограничение. Коммит также только по отдельной явной просьбе.
- Разработка и автоматические проверки локальные. Локальная production-сборка допустима только без подключения к production. Не считать имя переменной или скрипта доказательством локальности БД; проверить фактическую цель, не раскрывая секреты в отчётах.
- Миграции разрешены только из `main`. Для автоматических прогонов действует постоянное разрешение на **отдельную, изначально пустую, одноразовую локальную тестовую БД**, с проверкой хоста, точного имени, изоляции и пустоты. Разрешение не распространяется на production и удалённые БД. Основная локальная БД мигрирована 26.09.2026 по отдельному явному подтверждению; это не разрешение на будущие миграции пользовательских баз без проверки актуальных правил `AGENTS.md`.
- Схема — `src/db/schema.ts`; после изменения генерировать миграцию через `pnpm db:generate`, проверять результат, не писать и не править миграционный SQL вручную. Локальное применение — `pnpm db:migrate`. Указание удалённых инструментов в старых документах не даёт полномочий их запускать.
- Сохранять существующие незакоммиченные изменения. Не сбрасывать, не прятать и не переносить их в чистую рабочую копию ради удобства. Работа в этом чате и новом использует одну папку; не вести одновременные правки одного контура в двух чатах.
- Общаться по-русски, простым языком. Отчёты короткие: результат, важные ограничения, что не проверено, требуемые решения и действия. Подробные логи и полный перечень тестов — только если нужны для существенной проблемы или запрошены.
- Неоднозначную бизнес-логику согласовывать, а не угадывать. Можно задавать вопросы во время работы и продолжать независимые участки. Если пользователь не ответил, повторить вопросы в итоговом сообщении с указанием незавершённых частей. В обычном развёрнутом ответе собирать вопросы в конце, по возможности с примерами и предлагаемым вариантом.
- Нормальный масштаб — **200 000 стыков**, не 500 000. Проверять число запросов, сложность, объём ответов и отрисовки. Большой отдельный системный прогон на 200 000 ранее отложен; не представлять его выполненным. Эквивалентные проверки сложности/числа запросов обязательны; никакой нагрузки на production.
- Не считать старые тесты, код и руководство независимым подтверждением бизнес-правила. В спорных местах исходить из последних решений пользователя, фиксированных в итоговом плане. Не вводить скрытые исторические освобождения, не путать «не требуется» с «запрещено», ожидание с фактическим началом этапа, состояние линии с историей отдельного стыка.
- Пользовательские изменения сопровождаются обновлением встроенного руководства (`src/components/user-guide-page.tsx` и подключаемые разделы). Импорт/массовое заполнение/замена валидируют итоговую объединённую запись и показывают все одновременно обнаруженные ошибки. Системные поля не переносить в обычную форму стыка и не давать менять обходными путями.
- Изменение правил диспетчера для сохранённых записей требует повышения `DISPATCHER_TASK_CALCULATION_VERSION` и тестов формы/сервера, кода задачи, сохранённого индекса и `dispatcherTasks`. Дорогие расчёты объединять, изменение линии не должно перестраивать весь журнал; перенос стыка затрагивает обе линии.

### Проверки и два пользовательских промпта

- Во время реализации необходимы поэтапные проверки бизнес-сценариев, регрессии, typecheck, unit-тесты, локальная сборка и относящиеся к изменениям E2E, включая параллельные изменения, ошибки, отмену и повтор операций. Никаких обещаний безопасности только на основании зелёных тестов.
- **«Проведи полную предкоммитную проверку.»** означает полный риск-ориентированный аудит всех незакоммиченных изменений по `AGENTS.md`, а не только запуск тестов. В неоднозначной логике спрашивать пользователя. Для текущего обновления НЕ запускать его автоматически: сначала пользователь тестирует интерфейс и может попросить доработки.
- **«Проведи комплексный системный аудит логики и масштабируемости.»** включает независимую проверку бизнес-допущений и ожиданий тестов, сквозных сценариев, смежных правил и нагрузки. Эта передача не является запросом такого аудита.

## Б. Итоговый план обновления линий

Полная согласованная спецификация: [line-program-plan-2026-09-25.md](line-program-plan-2026-09-25.md). Читать целиком. Ниже только ориентиры, не замена спецификации:

- Постоянный реестр «Программа линий»; единый вход и вкладки «Линии», «100%-ные линии», «Процентные линии». Без оболочки статистического отчёта; сохранить быстрые назначения, поиск, расчёт по клеймам и полезные переходы. Ненастроенные требования — СП-02.
- С/У: общая взаимозаменяемая группа РК/УЗК/послойной замены и отдельная потребность ПВК. Послойная замена только У. Назначение относится к методу на всех применимых этапах, но выполненность этапов показывается раздельно.
- Дополнительное решение пользователя 26.09.2026: когда НК до ТО выключен, сохранённые результаты этого этапа остаются в истории, но временно не учитываются программой линий (ни выполненный ПВК, ни негодные результаты для добора). Повторное включение возвращает их в расчёт. Не удалять историю и не отменять общие назначения; ограничения послойного комплекта по имеющемуся браку этим не снимаются.
- В базе процента учитываются подходящие сваренные официальные актуальные записи, включая R/W/Y. Математическое округление с 0,5 вверх и минимумом 1 для положительной нормы на непустую группу; 0% и пустая группа дают 0. Это последняя версия правила, старое округление вверх отменено.
- Брак ВИК/РК/УЗК/ПВК на обоих этапах и в дублях влияет на добор общей группы по каждому отдельному негодному С/У, включая R/W/Y. Уточнение от 26.09.2026 отменяет прежнее исключение ремонтных потомков: негодные F1/F1R1/F1R2 считаются отдельно у официальных клейм, которыми сварена именно соответствующая запись, а не автоматически у клейм исходного F1. Несколько методов/этапов/дублей одной записи не умножают счётчик. При 0 < процент < 100 добор +1 при ровно 1%, иначе +2; четвёртый отдельный негодный стык, в том числе ремонт, запускает полный контроль по клейму и существующие действия по отстранению. При 0% добора нет. Базовый процент линии и процент ПВК автоматически не растут. У ПВК может расти число требуемых стыков вслед за ростом базы, в том числе при новых R/W/Y. ТВМТ и Т не участвуют в таком доборе.
- Явный послойный контроль требует ПВК = «да» и объединяет послойные ВИК/ПВК в неделимый комплект. Старой автоматики и глобального переключателя не будет. Все точки входа, атомарность, подтверждения, создание четырёх документов от основного результата ПВК и отдельное удаление описаны в плане.
- При послойном назначении негодные ВИК/РК/УЗК/ПВК запрещены **на обоих этапах и в дублях**, ТВМТ отдельный. Не перепутать с новой настройкой «ПВК — только годен»: она ограничивает наш ПВК, но сама по себе не запрещает негодный дубль. Настройку «Негодный ПВК увеличивает добор» не создавать.
- Согласованы серые зоны: обязательность для нескольких клейм общего стыка, лишний обычный ПВК после послойного назначения, зачёт проведённого негодного ПВК, замена невыполнимого ПВК после негодного ВИК, зачёт выполненного обязательного ПВК после отмены, отсутствие зачёта годного дубля вместо нашего контроля, защита удаления основного результата с послойным комплектом. Использовать конкретные примеры плана как приёмочные сценарии.
- Схема и проверяемый переход данных потребуются. Разовая очистка касается только старого автоматического послойного комплекта, не обычных результатов/документов. Подготовка и испытания локальные; фактическая production-очистка/миграция этим не разрешена.

Рекомендуемая последовательность уже зафиксирована в плане: независимые приёмочные примеры и общий расчёт → схема и тестовый переход → создание/редактирование/импорт и реестр → интерфейс → послойные процессы → диспетчер и индексы → руководство и поэтапные проверки → передача пользователю для тестирования.
