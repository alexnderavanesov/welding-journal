## Ограничения и организация дальнейшей работы

- Не начинать реализацию без новой прямой команды. После такой команды это **одна общая задача** с внутренними этапами; отдельно просить запуск каждого этапа не нужно. Вести связь «требование → изменение → проверка» по всем 22 пунктам и их подробным условиям. Не терять документы, импорт, справку и приёмку при сокращении пересказа.
- Пользователь для этой конкретной реализации доверил выбор подзадач с агентами или без них. Это исключение не распространяется на другие задачи; сохраняется экономный расход ресурсов. По умолчанию действует правило AGENTS.md о работе без субагентов. При этой передаче субагенты не запускались.
- Нельзя автоматически commit, push, deploy, менять production, получать свежий backup или выполнять удалённые команды. Старые разрешения и исторические команды не являются новым поручением. Production — реальная рабочая среда; read-only доступ не разрешает тесты, пересчёты или другие записи.
- Не менять ветку/checkout, не создавать worktree, не делать reset/stash, не удалять рабочие данные, изменения или артефакты проверок. Не останавливать/перезапускать серверы ради передачи. Макет на 4318 сохранять остановленным.
- После отдельного разрешения реализации локальные миграции уже разрешены без повторного согласования: только на `main`, с проверкой локального адреса и точного имени БД, сохранением данных и просмотром сгенерированной миграции. Источник схемы — `src/db/schema.ts`, затем `pnpm db:generate`, проверка, `pnpm db:migrate`; SQL миграций вручную не писать.
- Фикстуры, автоматические тесты и нагрузка — только отдельная изолированная одноразовая локальная БД с проверенным исходным состоянием. Основная рабочая БД не предназначена для фикстур. Production-БД — Selectel, `welding_journal`, приватная сеть; старое Yandex-подключение в `.env` не использовать. Перед любой отдельно разрешённой production-операцией сверить целевой адрес с текущим Coolify runtime. Секреты не переносить в документы.
- Все изменённые правила отражать во встроенном руководстве. Импорт/замена/массовые операции проверяют итог после слияния со старой записью, показывают все одновременно обнаруженные ошибки. Системные поля доступны только профильным процессам. Изменение правил диспетчера требует версии расчёта и проверки сохранённого/виртуального индексов.
- Chrome — основной браузер функциональных/нагрузочных проверок; WebKit — второй для затронутых общих процессов. Подробную матрицу установленного Safari не повторять без конкретной причины. Полный системный аудит не запускается автоматически.

## Согласованная единая задача: существенные правила

Подробные исключения, формулы, составы и примеры находятся в полном плане. Следующие решения особенно легко потерять при передаче:

- **Т/ОП:** кириллическое семейство Т и номера ОП, свободная основа номера; двусторонняя проверка имени/типа. Сохранённый стык нельзя перевести между Т и С/У, в том числе одновременной сменой номера и типа. ОП-13R5 нельзя превратить в S13R5. Проверять все входы и устойчивую идентичность цепочки.
- **Клейма:** заполненные корень/заполнение/облицовка имеют одно официальное клеймо; фактические — отдельно одно. Официальное и фактическое могут различаться, пустые слои разрешены. Все поля индекса 2 запрещены даже с тем же клеймом. Несовместимое сохранение блокируется, одного предупреждения недостаточно.
- **Допуски и ТК:** у однородного и разнородного Т только D1/T1 трубы, но проверяются обе указанные группы материалов и все участвующие способы. Одно официальное клеймо должно покрывать их. Сохраняются НАКС/ДЛС/отстранения и исключение для несвязанных исправлений существующего невалидного допуска. Для Т добавить весь процесс ТК: реестр, автоподбор, массовый подбор, применимость и ДЗ/СП, без ложной неполноты D2/T2. Автоподбор — при первом заполнении даты сварки, пустой ТК и единственной подходящей действующей карте; уже назначенную применимую карту не заменять автоматически.
- **Длина L:** только для Т, положительная или пустая, мм без округления. При дате сварки и пустой L сохранение разрешено, недостающее значение включить в **существующее СП-03**, отдельный код не вводить. Неизвестная длина не равна нулю. Каждый ремонт наследует полную L; изменение исходной L атомарно распространяется на цепочку. Отдельную длину фактически ремонтируемого участка не вводим. L — поле шаблонов; автоматическая пересборка всех документов не поручена.
- **Ремонты:** только «годен»/«ремонт», неограниченные R, без порога 89 мм и счётчика ограничения. РК, послойный контроль, вырез/W и катушка для Т запрещены во всех входах, включая дубли. ВИК обязателен, порядок ВИК → назначенный ПВК → УЗК, настройка «ПВК — только годен» сохраняется. ПСТО/ТВМТ, предварительный/основной НК, повторы и история используют существующие процессы и защиты.
- **Нормы опор:** по физическим соединениям, не по мм; отдельные УЗК и ПВК по клейму/линии. По умолчанию УЗК наследует общий процент РК/УЗК линии, ПВК — её процент ПВК, каждый минимум 0,5%. Независимое собственное значение 0,5–100%, живое наследование и возврат «Как у линии». Неизвестная настройка не равна нулю. `ceil(N × % / 100)`, при N=0 — 0; С/У-округление не менять. Нормативное обоснование 0,5% закрыто пользователем, документы не запрашивать.
- **Один физический ОП:** ОП→R1→…→R10 даёт одну единицу базы и максимум один зачёт каждого метода. Норму закрывает назначение, брак и переход на ремонт не требуют дополнительной опоры; «назначено + годно» не суммируется. Брак Т не создаёт добор Т или С/У; эскалация клейма С/У до 100% на Т не распространяется. Закрытый расчёт назначений не означает фактическое завершение контроля.
- **Статистика «Опоры»:** отдельная вкладка; физический основной объём один раз, текущие негодные исключены из выполненного и показаны отдельно, заваренные ожидающие включены. Период основного объёма — по дате сварки последнего ремонта, как в «Общей». Ремонты отдельно по своим датам и полной L: два ремонта опоры 600 мм дают 1200 мм ремонта. WDI не применяется. ЖСР/чек-лист/ЗНИ поддерживают ОП и L, пользовательские документы — текущий цикл, системные — свой исторический.
- **Интерфейс:** отдельная вкладка «Опоры» в работающей программе линий, с её таблицами/группами/назначениями/стилем. Обязательно «Можно снять» и «Расчёт итогов», защита черновиков и версий. Для каждого метода различать норму, достижимую потребность, назначения, зачёт, фактические результаты, «Лишнее», «Доп» и «Можно снять».

### Доработка 1: только заявка не запрещает снятие

Охват: основной НК, НК до ТО, **ПСТО и ТВМТ**, С/У и разрешённые методы будущих Т. Если есть только заявка без выполненной работы и прочих препятствий, разрешить `Да → Пусто`. «Можно снять» остаётся доступной для безопасного снятия частью «Лишнего», а не отдельной взаимоисключающей категорией. Уже сохранённые назначения «Ожидает НК» тоже должны получить новое поведение после пересчёта.

Пример: F1 РК в А1. При сохранении снять назначение, удалить только позицию РК F1 и её привязку/дату. Остальные методы/стыки/результаты не менять. Если позиций не осталось — безвозвратно удалить пустую заявку, без архива/корзины/истории «отменили заявку». Выбор в черновике ничего не удаляет. Изменения записи, документов и индексов атомарны; новый результат/изменение состава другим пользователем не должен допускать частичного сохранения или удаления факта. Снятие через «Пусто» не является официальной отменой и не уменьшает доступную базу Т.

Дата фактического ПСТО или диаграмма без результата недопустимы. Чтение штатных путей показало уже существующее требование/запись «проведено»; подтверждённого обхода пока нет. При реализации проверить остальные пути; найденный обход закрыть сохранением и существующим СП/ДЗ, не объявлять гипотезу установленным дефектом.

### Доработка 2: отменяется только будущая работа

- После собственного выполненного контроля — **годного или негодного** — «Отменен» недоступен и в программе, и в карточке, и на сервере/импорте/массовых входах. Очистка через «Пусто» тоже не обходит факт. Ошибочный результат исправляется профильным процессом. Будущая работа может относиться к уже существующему стыку.
- Общий флаг метода НК до ТО/основного НК нельзя отменить, если собственный факт есть на его применимом этапе. Отдельную отмену этапа не добавляем. Выполненный ВИК сам по себе не запрещает отменить ещё не выполненный УЗК.
- Частичное ПСТО линии: 3 из 10 выполнены — их факты/назначения/диаграммы сохраняются; отменяются только 7 подходящих невыполненных, с точным предпросмотром состава. Политика будущей потребности касается новых записей, но не отменяет выполненные, необходимые ТВМТ или обязательные повторы. Это допустимое смешанное состояние линии, а не ложная ошибка однородности.
- Отмена невыполненного УЗК/ПВК Т **не даёт зачёт**. Норма `ceil(N × % / 100)` остаётся; доступность исключает официально отменённые невыполненные методы. Потребность = `min(норма, доступное количество)`. 3 ОП, норма 3, назначены 3, одному отменили → зачтено 2, доступно 2, расчёт закрыт. При 10 ОП и норме 3 тот же случай требует ещё одну доступную опору.
- Старый пример «3 годных, потом одному отменили» **заменён последним решением**: отмена запрещена, остаются 3 факта/зачёта. Если норма затем стала 2, нужное превышение оформить «Дополнительным». Для Т это один выбранный механизм; он сохраняет зачёт/факт и выделяет «Доп», но не делает остальные превышения принятыми автоматически. Механизмы согласований С/У пока не меняем.
- По словам пользователя на production нет «годен (отменен)». Это **не проверенный факт**. В будущей локальной репетиции на свежей выгрузке проверить отмену вместе с собственным выполнением по методам/этапам/циклам, отдельно годные/негодные; записать дату выгрузки, число случаев, включая ноль. При находках сохранить данные и вынести решение, не делать автоматическую миграцию/архивный режим отсутствующего сценария. Подписи, СП-11, специальный отчёт отменённых годных, фильтры и руководство согласовать с новой моделью.

### Расчёты, справка и наследование

- «Показать стыки в рабочей таблице» должно раскрыть раздел/группы/линию/клеймо до **точного полного состава** расчёта, а не только 50 записей текущей страницы. Дождаться загрузки, прокрутить/сфокусировать, сохранить совместимые фильтры и черновики; нулевой состав — недоступная кнопка с причиной. В коде замечены доступность кнопки при 0 и отображение некоторых специальных составов как `all`; каждый случай нераскрытия ещё не воспроизведён.
- «Источники добора» — первичный брак РК/УЗК С/У, уникальные физические источники с применимыми этапами/дублями; не количество ремонтов/заключений. Действующие +1/+2 и четыре источника→100% не меняются; Т в доборе не участвуют.
- Поиск линии в «Расчёте итогов» **над списком**, по всему набору, не только странице. Иконка, очистка, счётчик, сохранение поиска/показателя при возврате. **Общий итог не меняется**, основной поиск страницы не затрагивается; без запроса стыков каждой линии.
- «Правила системы» перед «Руководством», подвкладка «Соединения», доступ всем вошедшим без новой галочки прав. Четыре колонки параметр/С/У/Т; общий поиск и совместные фильтры столбцов. Одинаковые соседние значения визуально объединяются, но полный текст остаётся в каждом исходном столбце для поиска; никаких «То же». Примечания после таблицы доступны и при фильтрации.
- Двусторонние кликабельные переходы «допуски → Справочники → Параметры проверки» и обратно, прямые URL/назад/обновление/клавиатура. Чтение справки не даёт прав на закрытые реестры. Обновить все параметры, схемы и «Разобрать свой пример» для Т D1/T1, обеих групп и одного клейма; скрытые прежние D2/T2/второй сварщик не влияют после переключения из С/У. Встроенное руководство входит в эту же задачу.
- **Наследование не переделываем.** Отличать начальное копирование назначения от обязательности по своей действующей официальной ветке. У нового официального S1 после неофициального негодного S1 копируется РК=да, но прежний брак сам по себе не делает РК обязательным. Обязательства других действующих официальных предков остаются. Если после снятия РК вернуть официальность прежнему предку, перестройка в R/W возвращает обязательность, поле может остаться пустым и появляется **СП-08**. Автозаполнение/дополнительное окно пока не делаем.
- Согласованная пара РК+УЗК и «Да+Доп» могут одинаково убрать лишнее сочетание, но пара делает оба метода обязательными на R/W; «Доп» сам по себе — нет. Собственный брак дополнительного метода создаёт обязательность. Оба механизма и эти различия пока сохраняются, упрощение отложено.

### Проверка будущей реализации

Пользователь требует глубокую предметную и пользовательскую приёмку **всех** согласованных правил, сценариев и способов обхода: UI и прямой сервер, создание/редактирование, импорт итоговой записи и совместные ошибки, массовые операции/замена, официальность/цепочки/удаления, этапы/дубли/повторы, свои и унаследованные факты, настройка off/on, устаревшие/параллельные клиенты, повтор/отмена и атомарный откат. Проверить документы, расчёты/статистику, СП/ДЗ, сохранённый и виртуальный индексы, регрессии С/У и текущие разрешения. Ожидания выводить из решений пользователя, не только из существующих тестов.

Сложность и пакетность растущих путей — с учётом 200000 записей; это не разрешение нового отдельного большого системного/нагрузочного аудита. Локальная репетиция на свежей выгрузке запланирована, **не выполнена**; выгрузка в этом обсуждении не получена. Получение production-backup требует отдельного конкретного разрешения.
