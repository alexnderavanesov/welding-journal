## Обязательные ограничения

- Не реализовывать, не запускать аудит/тесты/миграции и не править планы до новой команды. Не делать автоматические commit, push, deployment, stash/reset, смену ветки, новый worktree/checkout, остановку серверов, архивацию или сообщения старому чату. Сохранить все рабочие данные, незакоммиченные изменения и игнорируемый макет. Оба чата используют общую папку: не вести одновременные записи или два runner одной тестовой БД.
- Production, включая `welding-journal-test.yums.ru`, доступен только для релевантного просмотра без изменения сохранённого состояния. Это не разрешение тестировать, пересчитывать, получать резерв, менять данные/код/схему/инфраструктуру или делать push с автодеплоем. Конкретное действие требует отдельного прямого поручения. Для передачи обращаться к production не нужно.
- Fixtures, автоматические и нагрузочные проверки — отдельная проверенная пустая локальная БД и отдельное хранилище шаблонов. Рабочая `welding_tracker` не тестовая. Перед будущим запуском заново проверить точный host/имя/изоляцию/владение. Здесь базы не опрашивались и не менялись.
- **Постоянное разрешение на проверенные локальные миграции сохраняется**, когда реализация отдельно поручена: только `main`, сохранить данные, schema Drizzle → штатная генерация → просмотр → штатная миграция. SQL миграций вручную не писать. Не спрашивать повторное разрешение на уже согласованный локальный шаг; чтение контекста само по себе его не запускает. Remote/production-миграции требуют отдельного конкретного разрешения.
- Новые функции/правила/настройки отражать во встроенном руководстве. Системные поля менять только профильными workflow; импорт проверять по итоговой записи после слияния, показывая все совместные ошибки. Изменение правила диспетчера требует версии расчёта и регрессий сохранённого/виртуального индекса. Сохранять атомарность, версии, историю и масштаб около 200000 стыков.
- Приоритет пользователя — внимательность и сохранение всего функционала; не обещать безусловную плавность по демо или одному замеру. Модель/настройки не переопределять; не привлекать агентов на основании старых поручений прошлых аудитов.

## Завершено: фон и новая незакоммиченная работа

Предыдущие этапы уже в истории Git: журнал AG Grid — `f57acfac`, документы — `04cdb115`, программа линий/назначения и переходы отчётов — текущий `2ffdb076`. [Аудит 19.10](precommit-audit-2026-10-19.md) относится к последнему из этих этапов, **не** к новым итогам групп. Старые записи «перенос программы/документов не начат» и «их аудит впереди» больше не актуальны. ПСТО/ЛНК остаются на прежней таблице.

Новая реализация, одобренная пользователем, сделана **только для журнала**:

- Итоги стоят в соответствующих столбцах и выровнены **слева**, в том числе при закреплении/перестановке. Линии различаются по проекту/шифру/обозначению; при группировке по самой линии показано её имя.
- «Стык» и WDI считают **физические соединения**, не строки ремонтов/вырезов. После замены катушкой старый физический стык исключён, две стороны считаются отдельно. Даты — min/max всех входящих записей; проект/шифр показываются при полном совпадении.
- «Ошибка» важнее всего, **включая исторические записи**, чтобы пользователь устранил её. Затем ранний незавершённый этап (сварка, ремонт, заявка, НК) + отдельный счётчик оставшегося брака; без ожиданий брак даёт «не годен».
- Полная годная цепочка ремонта считается годной, несмотря на брак предшественников. Аналогично обе годные стороны катушки; заменённый старый стык не ухудшает итог. Неполная/неоднозначная цепочка не выдаётся за полностью годную; ошибки истории не скрываются продолжением.
- Фильтр «не годен» выбирает **индивидуальные записи стыков**, не агрегаты групп. Итоги пересчитываются по загруженной отфильтрованной части. После фильтра могут быть видны отвергнутые предшественники прежде годной группы. Галочки/операции выбирают записи, не физические корни.
- Сводная логика: `src/lib/weld-group-summary.ts`; ячейки: `src/components/welding-journal-group-summary.tsx`. Контекст физического корня, WDI и сохранённой замены: `src/server/journal-group-context.ts`, один пакетный запрос по ID страницы, подключён к двум путям чтения журнала. Группировка/выбор не вызывают RPC на строку. Правила диспетчера и схема БД не менялись.
- Сопутствующие исправления: раскрывающая стрелка группы обновляется; служебный столбец при скрытии всех данных не попадает в сохранённый вид; отложенное восстановление фокуса после формы не отнимает его у уже активной ячейки. Руководство обновлено.

Сохранить границы отчётов: в журнале серверный поиск/фильтры/сортировка охватывают всю выборку, группы и выбор галочками — загруженную часть. В документах отдельно согласован SSRM с серверными группами и счётчиками всей выборки, галочки по-прежнему выбирают загруженные документы; это не основание менять модель журнала. В программе линий фильтры/группы обзора относятся к показанной странице, поиск раздела и сводки — всему отбору.

## Бизнес-основа для будущего переноса

Профильные workflow сохраняются. В четырёх сценариях ПСТО/смены линии исходно **KEEP**, решение отдельно по стыку, весь имеющийся комплект, включая заявки без результата; целевой этап, собственная история, хронология, официальность и зависимости проверяются.
